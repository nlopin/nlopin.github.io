01 · 15 min · practice

Cold open: keyboard only

Goal: students feel why semantics and focus styles matter before any theory.

  • Show the setup slide first. On a Mac, Safari and Firefox skip links on Tab until it's switched on. Without it, the first 10 minutes are lost.
  • Four tasks:
    • gov.uk: when does someone born 15/10/1966 get a free bus pass? The good baseline. It starts at the homepage, so finding the tool is part of the task (the slide hints "pension calculator"): it's the State Pension age calculator, option "bus pass". Answer: 15 October 2033, in England.
    • renfe.com: a train search
    • ikea.com: a desk under €100 into the cart, then open the cart
    • idealista.com (idealista.es redirects there): the list of apartments for rent in Barcelona, then open the 3rd result
  • Walk around the room. Point out the cookie banners: they're usually the first thing that fails.
Talking point

Don't explain anything yet. When someone says "I'm stuck", answer "write down where". Collect the worst failures on the board under the four debrief questions (couldn't reach, Tab jumped around, stuck, focus vanished); the next block is built from them, one pitfall per question.

02 · 12 min · theory

Interactive HTML, driven by the debrief

Goal: every failure from the cold open gets a name and an HTML cause. The "Common pitfalls" slide is the map for the whole block: each following slide's kicker says which pitfall it answers.

PitfallSlides
1. Couldn't reach itA div is not a button → Link or button? → Both, side by side (gov.uk cookie banner) → Looks like a button, is a link ("Start now")
2. Tab jumped aroundFocus order is source order. tabindex above 0 is almost always wrong.
3. Stuck in a bannerA real modal keeps focus: <dialog> with showModal() moves focus inside, keeps Tab inside, closes on Esc and returns focus (teaser only).
FormsNot a pitfall they hit: sighted keyboard users see labels. Opens with the unstyled signup form, "the form you style at the end, and what makes its HTML right", framed as what the gov.uk calculator does right. Includes <select> and <details> (Controls that come ready-made).
4. Focus vanishedThe bridge slide: back to the signup form. "The HTML is right, it looks like 1995, and one line of CSS hides the focus ring." Straight into CSS. Paid off later on two slides with the same kicker: :focus vs :focus-visible (selectors) and Outline is not part of the box (box model).

Talking points

  • Link vs button: go somewhere vs do something. An <a> without href can't be focused.
  • The gov.uk screenshots are from the cold open. If someone inspects "Start now": it's <a href role="button">. gov.uk adds the role so screen readers call it a button, which is a debated design-system choice. Plain <a href> is the right default.
  • Label ↔ input via for/id: a bigger click target, and the name a screen reader says. name is the key the form sends.
  • Input types bring the right mobile keyboard and validation. required, autocomplete, placeholder only for an example value.
  • <fieldset> + <legend> for radio buttons: same name means one group.
  • Demo: open form-exercise.html unstyled, fill it, submit. Read the query string in the address bar: forms work without JS. The gov.uk calculator does the same: the answers end up in its URL (/state-pension-age/y/bus_pass/1966-10-15).
  • The gotcha: <button> inside a form defaults to type="submit".
  • ✂ cut The "Controls that come ready-made" slide (<select>, <details>). Keep the <dialog> slide: it answers pitfall 3.
Common misconception

"Accessibility is an extra feature we add at the end." No: picking the right element gives it for free, and picking the wrong one makes it expensive. Glafira Zhur's guest lecture on October 5 goes deeper.

03 · 10 min · theory

What CSS is, why it exists

  • HTML is meaning, CSS is presentation. Show tweakcn.com, and switch between 2–3 theme presets: same components, only the CSS changes.
  • Demo: turn CSS off on a news site (Firefox → View → Page Style → No Style). It's still readable because of its semantics.
  • The user agent stylesheet: why h1 is big with no CSS. Show it in the Styles panel.
  • Three places CSS can live. We use <link rel="stylesheet">: one file for many pages, cached.
  • Live canvas: open live-canvas.html (no styles), then add the block 3 chunk: a font-family on body. The whole page changes, which proves the link works.
04 · 7 + 8 min

Anatomy of a rule, inheritance, quiz

  • Parts: selector, declaration block, declaration, property, value, and the rule as a whole.
  • CSS forgives silently: an unknown property is skipped. A missing ; merges two declarations into one invalid one, and both are lost. Show the crossed-out ⚠ in DevTools.
  • Inheritance: color, font-*, line-height pass down; margin, padding, border don't.
  • Live canvas: block 4 chunk. Uncomment the body { border } line to show only the body gets one, then delete it.
  • Quiz: 6 slides with the same snippet and a different part highlighted in each. The room shouts the answer, then you click "Answer".
05 · 15 min · theory

Selectors

  • Simple selectors: type, class, id (explain why to avoid it for styling), *, attribute.
  • Combinators: descendant, >, +, ~. The comma is a list, not a combinator.
  • Pseudo-classes for state. Here the recap pays off: :focus-visible, :checked, :required, and :invalid vs :user-invalid.
  • Pseudo-classes for structure. ✂ cut :has() is optional.
  • :focus vs :focus-visible: why designers remove the ring (mouse clicks) and why they don't have to.
  • Pseudo-elements: two colons, a part of an element.
  • Live canvas: block 5 chunk. Live-code each selector type as you introduce it.

CSS Diner comes after block 6: its later levels need a feel for which selector matches what, and the break follows it.

06 · 6 + 4 min

The cascade and specificity

Goal: when two rules disagree, students can predict the winner and read it in DevTools.

  • Open with a prediction: p { color: red } and .intro { color: blue } on <p class="intro">. Hands up for red, then for blue. It's blue.
  • How the browser picks a winner, in order:
    1. Origin and importance: your stylesheet beats the browser's; !important beats both. (Strictly, the browser's own !important rules win over yours, but students won't meet those.)
    2. Specificity: the more specific selector wins.
    3. Source order: if they tie, the later one wins.
    A style="" attribute beats any selector. An inherited value loses to any rule that targets the element directly, even *.
  • Specificity is three numbers, compared left to right: ids, then classes/attributes/pseudo-classes, then types/pseudo-elements. * and combinators count zero. There's no carrying: 11 classes never beat 1 id.
  • Which rule wins? 3 predict slides:
    • a:hover (0-1-1) beats nav a (0-0-2).
    • The same selector twice: the later one wins.
    • #nav a (1-0-1) beats .menu .link.active (0-3-0).
  • Keep specificity low: style with classes, avoid ids, avoid !important. DevTools → Styles lists the matching rules with the winner on top and the losers crossed out.
  • Live canvas: block 6 chunk. Add a { color: … } after the nav a { color: inherit } from block 5. The nav links stay dark even though the new rule comes later. Inspect a nav link to see the a rule crossed out.
  • CSS Diner (12 min): levels 1–16 for everyone. Levels 13–15 (the sibling combinators) are where students usually get stuck.
Common misconceptions
  • "The last rule always wins." Only between rules of equal specificity.
  • "!important fixes it." It wins this fight and starts the next one: the only way to beat it is another !important.
  • "More selectors in a rule means more specific." It's what kind they are: one id outweighs any number of classes.
07 · 10 + 8 min

Units and colors

  • px vs rem / em / % / vw / vh / ch. ✂ cut dvh.
  • Why rem: the user's default font size setting. Zoom scales everything, so zoom doesn't show the difference; the font size setting does.
  • em compounds in nested lists; rem doesn't.
  • max-width: 65ch on the canvas is an instant, visible improvement.
  • Colors: named, hex, rgb(), hsl(), alpha, currentColor. ✂ cut oklch().
  • Why HSL: change only the lightness to get the hover and active shades.
  • Contrast: 4.5:1 for body text, 3:1 for large text and UI parts. Show the ratio in the DevTools color picker.
  • Live canvas: block 7 chunk.
  • Practice: px-vs-rem.html: change the Chrome font size and see which line grows. The em/rem lists print their computed sizes. Then fix the low-contrast paragraph.
Common misconception

"rem vs px is taste." No: the px version ignores a setting that people with low vision rely on.

08 · 8 min · theory

Flow layout

Taught before the box model on purpose: margin collapse and inline padding only make sense once block vs inline is clear.

  • Normal flow: block boxes stack in the block direction; inline boxes wrap along the inline direction.
  • Block vs inline, and which elements are which.
  • Predict: width on a span. Then show flow-and-box-demo.html §1.
  • Directions depend on the language: demo §5 switches writing-mode and dir. ✂ cut Logical properties are a teaser only.
  • display: none also removes the element from the accessibility tree, which ties back to block 2.
  • Live canvas: block 8 chunk: nav li { display: inline }, then the .cta first as inline (padding overlaps the lines), then as inline-block.
09 · 13 + 5 min

Box model

  • Content, padding, border, margin. Hover each layer in the Computed box diagram.
  • Shorthands go clockwise from the top. margin-inline: auto centers a block.
  • Predict quiz (3 slides):
    • The gap between two p with margin: 20px 0 is 20px (collapse).
    • An inline a with padding: 20px doesn't make the line taller.
    • width: 200px; padding: 20px; border: 5px renders 250px wide.
    Demos §2–§4 measure each of these live.
  • box-sizing: border-box and the universal reset.
  • Outline is not part of the box, which closes the loop with the cold open. Demo §6: focus with a border shifts the text, focus with an outline doesn't.
  • Live canvas: block 9 chunk. The 65ch from block 7 plus margin-inline: auto centers the column.
10 · 27 + 5 min · pairs

Style the signup form

Starter: form-exercise.html + form-exercise.css. The HTML has correct semantics (labels, a fieldset, email/tel/date inputs, a select, a textarea, a required checkbox, a <details>). The starter CSS includes *:focus { outline: none; }.

  • Pairs: driver types, navigator reads the checklist, swap every 10 minutes.
  • The checklist is on two slides: structure (items 1–4) and states (items 5–7). Item 7 bans ids and !important, so the cascade block gets practiced.
  • Stretch: label:has(:checked) for the chosen ticket, and make it work with dir="rtl" by using logical properties.
  • Show and tell: two pairs share their screen. Someone else in the room completes the form keyboard-only. DevTools → Rendering → "Emulate a focused page" keeps focus visible while you talk.
What to look for while walking around
  • Using :invalid turns every required field red on load. Point them to :user-invalid.
  • A :focus-visible rule that "doesn't work": it's losing to a more specific rule. Have them find the crossed-out declaration in Styles.
  • Radio labels are inline, so they wrap onto one line. Fine, or display: block on them.
  • width: 100% on inputs plus padding overflows without the border-box reset. It's a useful mistake: let them hit it.
  • Contrast checks on the placeholder color too (::placeholder).

Exit ticket and homework

  1. Name the parts of p { margin: 1rem; }.
  2. Why <button> and not <div>?
  3. A hovered nav link: nav a or a:hover, which wins? (a:hover, 0-1-1 vs 0-0-2)
  4. width: 100px; padding: 10px with border-box: how wide? (100px)

Collect the answers on paper or in a poll. Whatever most people got wrong opens lecture 3.
