Working with mobile devices

Without one line, every phone pretends to be 980px wide

no viewport tag

with it

In 2007 the web had no mobile sites, so the first iPhone laid every page out at 980px and shrank it. Phones still do that, unless you tell them: my page is ready, use your real width.

A device pixel ≠ a CSS pixel: a 393px-wide iPhone has 1179 pixels across (ratio 3). Your CSS, your media queries and vw all count CSS pixels.

Media queries · press → to read it

A media query asks the window a question

@media (width >= 40rem) { /* ordinary rules */ }
@media: "only if…". The rules inside are normal CSS that switch on and off.
width >= 40rem: the condition. Older spelling: (min-width: 40rem). Same answer.
Inside: no new specificity, no magic. If the answer is yes, the rules join the cascade.

Three steps highlight the three parts. The range syntax (width >= 40rem) works in every current browser (since 2023); min-width works everywhere including old ones. Both are fine.

The third point is the trap for later: a media query adds NO specificity. Quiz in two slides.

Breakpoints

A breakpoint is where your design breaks, not where a phone starts

  • Find it by dragging. Narrow the window until something looks wrong. That width is the breakpoint.
  • In rem, not px. Someone with a bigger default font gets the phone layout sooner, which is exactly what they need.
  • As few as you can. Two or three. Each one is a whole extra design to test.
  • Not device names. There are thousands of screen widths. "iPhone 15" is out of date next year.
  • You can't put var(--bp) in a query. Write the number, and a comment.

The rem point is the masters-level one: in media queries, rem/em are based on the browser's default font size (the user setting), not on your html { font-size }. A user with 20px default gets the 40rem breakpoint at 800px instead of 640px: their text is bigger, so they need the narrower layout longer. With px breakpoints they'd get cramped columns.

Exercise 1 case 2 asks them to find the breakpoint by dragging (34rem).

Live · drag the width slowly

A breakpoint jumps. A fluid value slides.

vw = 1% of the window's width. Mixed with rem, it makes a value grow with the window.

Drag across 800px. The top one jumps from 40 to 80px in one pixel of window; the bottom one grows a little with every pixel. Nobody notices a value that slides; everybody notices one that jumps. This act is the tools to make values slide: calc, viewport units, min/max/clamp.

Values built from parts · calc · variable fragments

CSS can do maths, with units the browser only knows later

calc() mixes units

The browser solves it at layout time, when it knows what 100% is.

A variable can be part of a value

One number per category; three colours each, built from it.

calc: spaces around + and − are required (calc(100%-2rem) is invalid). Inside min(), max(), clamp() you can write maths directly, no calc needed.

Fragments: --hue: 30 is just a number; it becomes a colour only inside hsl().

Clamping values

clamp(): be this, but never less than that, never more than this

MINPREFERRED → slidesMAX too small → MINtoo big → MAX

min() picks the smaller, max() the larger. Counter-intuitive: min() sets a maximum ("never more than 40rem"). clamp is the combination. If MIN > MAX, MIN wins.

The min(100% - 2rem, 40rem) line replaces a max-width + padding + media query combo.

Responsive typography

Text size belongs to the reader first

  • Everyone has a default font size in their browser settings: 16px, unless they changed it. People who changed it needed to.
  • rem follows that setting. px ignores it. Font sizes in rem.
  • Zoom is the other dial: it makes CSS pixels bigger, so the window gets narrower in CSS pixels, and your phone layout may kick in on a laptop. That's correct.
  • A size made only of vw ignores both dials: zoom makes the window narrower by exactly as much as it makes the pixels bigger. The text never grows.

WCAG 1.4.4 Resize Text: text can be resized to 200% without loss of content. font-size: 4vw fails it. The fix is a rem part in every fluid value (next slide), and the calculator shows a zoom test.

Fluid typography · where the numbers come from

Two points make a line. clamp() stops it at both ends.

The maths, once: from 40px to 96px is +56px over 920px of window: 0.0609 px per px, i.e. 6.09vw. At 360px that part is 21.9px, so the line starts at 40 − 21.9 = 18.1px = 1.13rem. Nobody does this by hand: next slide.

Why a fixed part and not just vw: any fixed part (px or rem) still grows when someone zooms; vw alone never does. Why rem rather than px: rem also follows the reader's default font-size setting, the other dial from the previous slide.

The DOM · type along: presets, then your own lines

HTML is text. The browser turns it into a tree of objects.

The DOM = Document Object Model. Every tag became an object (an element), nested like the HTML. JavaScript sees the objects, not the text. Click each preset; the changed lines flash red in the tree and the page changes with them. Hover a tree line to find its element.

Then do the break mystery live on the real showcase page in a second tab: F12 → Console → change the h1. Students type along in their own browser. Playground: playgrounds/dom-lab.html.

Find · the specific methods

One method per kind of question

  • getElementById → one element or null. Ids are unique, so it's the fastest lookup.
  • getElementsByTagName, getElementsByClassName → an HTMLCollection: live, it changes when the page changes. No forEach; use for…of.
  • Each one answers one kind of question. Next: one method for any question.

These are older than querySelector and you'll see them in every codebase and Stack Overflow answer. getElementById is still common. The live collection is the one surprise: add a card and titles.length grows by itself. querySelectorAll returns a snapshot instead.

Find · callback to Lecture 2

querySelector: one method, any CSS selector

  • Any CSS selector works: [data-tag="food"], :has()…
  • querySelector → one element or null. "Cannot read properties of null" = nothing matched.
  • querySelectorAll → a NodeList: a snapshot, it doesn't update. Has forEach.
  • el.closest(".card"): climb up to an ancestor.

Lecture 2's "a selector is a question to the DOM" pays off here: same question, now from JavaScript. Every live editor tonight explains the null error in plain words when it happens.

Change · text

textContent for their words. innerHTML only for yours.

  • textContent sets text. Whatever is in the string, it stays characters.
  • innerHTML parses the string as HTML: tags become elements, attributes become event handlers.
  • Anything a visitor typed is theirs. Putting it in innerHTML lets them run code on your page for other visitors: XSS, cross-site scripting.

This is the security habit to form on day one. Night Shift message 10 and Exercise 4 case 5 make them fall into it and climb out.

Change · state · the bridge to Part 1

JavaScript flips the state. CSS draws it.

A class is a fact; the stylesheet draws it. Attributes work the same way: next slide. Avoid el.style.color = …: it hard-codes the look into the script. The bridge: Part 1's attribute selectors and custom properties are now the interface between script and style.

Change · attributes · data-*

Attributes: read, write, remove

  • Values are always strings: "12", "false".
  • Boolean attributes: present = on. setAttribute("hidden", "false") still hides.
  • data-*: your own facts on the element.
  • CSS reads them too: [aria-expanded="true"], [data-saved].

Attribute vs property: common attributes are mirrored as properties (input.disabled = true, nav.hidden, link.href), with real types. The one that bites: input.value is what's typed now; getAttribute("value") is the value the HTML started with. aria-expanded is the menu's state in Exercise 3: a screen reader announces "Menu, collapsed". dataset drives the filter (data-tag) and the jam's ♡ save.

Listen · anatomy · press → four times

You don't call the function. The browser does, later.

who: the element to watch. Found with querySelector.
what: the event's name, as a string. A typo ("onclick", "Click") fails silently.
then what: a callback. The browser runs it on every click.
event: each time, the browser hands you a report: event.target (where), event.key (which key), event.preventDefault() (cancel the browser's own plan).

The mental shift from scripts that run top to bottom: the code inside the arrow function doesn't run now. It's a callback: you give it to the browser. Common bug: addEventListener("click", doThing()), with brackets: that calls it immediately and hands over its result.

Before you start · debugging in one slide

It doesn't work. Which of three?

a red error

Read the line

Cannot read properties of null: the selector matched nothing, or the script ran before the HTML (defer). Anything else: the line number is where it broke.

Log first

Make console.log("here") the first line of the listener. No log? Wrong element or a misspelled event ("Click"). A log but no change? The change is wrong: check what you set.

it blinks

The page reloaded

A form submitted (or a link was followed): everything your script did is gone. event.preventDefault() in the submit listener.

Forms · the default action

A form already works without JavaScript. That's the problem.

  • Submit (button or Enter) → the browser collects the fields, sends them to the action URL and loads a new page.
  • No action? It reloads this page. Everything your script did is gone.

Listen on the form for submit, not on the button for click: the click comes before the browser checks required and type="email"; submit only fires after they pass.

Why not click: pressing Enter in a field also fires a click on the submit button (so that's not the reason), but the click happens before validation. A click listener with preventDefault switches off the browser's required/email checks; a submit listener only runs on a valid form. In Week 3 you'll send this data to a real server with fetch, still from this same submit handler.

Reading a form · live · predict first: what does typeof print?

FormData: every field, by its name

Before pressing: "guests is a number field: what will typeof say?" Then press Reserve. Point at the second line: "2" string. Every value from a form is a string, even type="number". Number() before maths: "2" + 1 is "21". Unticked checkboxes aren't in the FormData at all (null). Fields without a name aren't either: the most common "it's null!" bug.

The market jam · deal the tasks

Five features the market is missing

  • Light, auto, dark ★★☆ — a 3-way theme switch that can follow the system.
  • My night ★★☆ — ♡ save stalls, count them, show only those.
  • What's on? ★★☆ — a time slider; the schedule fits a phone.
  • Ticket wizard ★★★ — the ticket form in 3 steps, with a review.
  • The map talks ★★☆ — click a zone, a panel (a bottom sheet on a phone).

Either let groups choose (first come, first served) or press 🎲 to deal them. Every task has HTML (new elements, with aria), CSS (a query, a variable or a :has) and JS (find · listen · change), so every group touches both halves of today. The reference version of all five on one page: project/jam-reference/ (teacher only, not in the student repo). A sixth group, or one that finishes early, gets a spare: Find a stall (★☆☆, live search) or Register a stall (★★★, a form that adds a card).

The market jam · show & tell

Two and a half minutes per group

  1. Demo it at phone width and desktop width.
  2. The code: what you find, which event you listen for, what you change. Show those lines.
  3. One CSS decision: the query, variable or selector that draws it.
  4. One bug you hit, and how you found it.

Then the class asks one question. Order: 1 → 5.

~2:30. Groups present from the driver's laptop on the projector (or open their folder on the teacher's machine). Double-click the timer to reset it between groups. Ask the question yourself if the room is quiet: "what happens if both the filter and your feature hide a stall?" for 2; "what does Enter do on step 1, and why?" for 4; "why a button and not a div?" for 5; "what's the difference between the choice and what the page shows?" for 1.

Today, in one slide

The page asks the world. The script listens to the person.

Part 1 · CSS · who are you asking?
  • @media the window · clamp() nobody
  • reading list: @container, @supports
  • Fewest questions wins: fluid first.
Part 2 · JS · find · listen · change
  • querySelector · addEventListener
  • classList / attributes: JS flips state, CSS draws it
  • Their words in textContent, always.

They meet in the middle: a class, an attribute, a CSS variable. That's the contract between your script and your stylesheet.

~2:45, right after the last group. If one slide stays in their heads, it's this one. For the curious: JavaScript can ask CSS's question too, matchMedia("(width >= 40rem)").matches, and set CSS's variables (style.setProperty, Ex 3 bonus 6).
