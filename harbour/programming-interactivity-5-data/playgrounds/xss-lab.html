Security · XSS

XSS lab

Cross-site scripting: user input ends up in the page as HTML, so the browser parses it, and any markup or event handler in it becomes part of your application. Below, the same "register a stall" input is rendered twice: on the left with an innerHTML template string, on the right with textContent. Both previews belong to a logged-in organiser whose session token is in memory. Anything the injected code sends out shows up in the attacker's log at the bottom.

The previews are sandboxed iframes and outgoing requests are intercepted, so nothing leaves this page and nothing here can touch the rest of the site. For the stored variant (saved in localStorage, re-runs on every reload), see the guestbook demo.

list.innerHTML += `
  <li class="stall" title="${stall.name}">
    <h3>${stall.name}</h3>
  </li>`;

textContent nothing sent

const li = template.content.firstElementChild.cloneNode(true);
li.title = stall.name;
li.querySelector("h3").textContent = stall.name;
list.append(li);

Try this

  1. Formatting: the left side renders bold text. Harmless, but it proves the input is parsed as HTML.
  2. onerror: the image fails to load, the handler runs, the session token appears in the attacker's log. No click needed.
  3. <script>: nothing runs. Scripts inserted with innerHTML are never executed, which is why filtering out <script> is not a defence: preset 2 didn't need one.
  4. Fake login: no JavaScript at all, just injected markup. A convincing form on your domain, pointing at someone else's server.
  5. Attribute breakout: the input closes the title="…" attribute and adds its own onmouseover. Hover the left card. Escaping depends on where the value lands: text, attribute, URL.
  6. Press Register a few times on the left with preset 2: every render re-parses the whole list (+=), so each payload runs again.

Defences, in order of preference

1 · Don't parse user input as HTML

textContent, createElement, setAttribute, a <template>. Values stay values in every context. This is what today's card() does.

2 · If you need HTML, sanitise it

For rich text from users: DOMPurify, or the Sanitizer API (element.setHTML()) where supported. Never a hand-written regex.

3 · Content Security Policy

A response header that blocks inline handlers and scripts from other origins. A second layer, not a fix: it limits the damage of a bug you didn't catch.

4 · Keep secrets out of reach

Session cookies with HttpOnly can't be read by JavaScript. Tokens in localStorage or in memory can: XSS reads them.
