Objects

A card in HTML is an object in JavaScript

Presentation

Data

The HTML mixes data with presentation ("from €8"). The object holds only the data, with real types: 8 is a number, false a boolean.

Property access: stall.name, or stall["name"] (both work; the bracket form is for keys in a variable: stall[key]). Keys don't need quotes. The trailing commas are allowed and make diffs cleaner.

The id matters later: it's the one field that never changes, so it's what we'll save and look things up by.

Higher-order array methods

map, filter, find

.map

🥟🎵🍹→ABC

Transform each element. A new array, same length.

.filter

🥟🎵🥟→🥟🥟·

Select by a predicate. A new array, same length or shorter.

.find

🥟🎵🍹→🍹

First element matching a predicate, or undefined.

None of them mutates stalls. They chain: stalls.filter(…).map(…). Also handy: some, every (true / false), reduce (one value).

Each takes a function and calls it once per item; you never write the loop. reduce exists; for a sum it's fine, for anything else a for…of loop is often clearer. Don't spend time on it.

Quick check · sort

What does this print?

[1, 10, 100, 9], twice. Without a compare function, sort compares items as text: "10" comes before "9".
And prices changed too: sort sorts in place and returns the same array.
[...prices].sort((a, b) => a - b): copy, then compare as numbers. Or prices.toSorted((a, b) => a - b).

Predict first. The in-place part is the one that bites in a UI: sort the stalls for one view and every other view is sorted too. reverse, push, splice also change the array; map, filter, slice, toSorted don't.

Coming from other languages

Six things that work differently in JavaScript

1 · truthiness

[] and {} are truthy. Falsy: false 0 "" null undefined NaN. Check emptiness with list.length === 0.

2 · equality

Always === ("2" == 2 is true). Objects and arrays compare by identity: [1] === [1] is false. A single = assigns.

3 · const

const prevents reassigning the binding, not mutating the object: state.tag = "food" is fine. let for reassignment. No var.

4 · strings from forms

"14" + 2 is "142". Every form value and every dataset value is a string: Number(input.value).

5 · ?. and ??

stall?.name: undefined instead of an error when stall is missing. x ?? "all": the default only for null / undefined.

6 · returning an object

(s) => { name: s.name } returns undefined (braces are a body). Wrap it: (s) => ({ name: s.name }).

Every card is a bug they would otherwise meet this week. 2 and 4 are in the bug hunt at the end of the day. Spread · destructuring · template literals

Don't mutate your inputs

Pure functions

A function that reads its arguments and returns a new value, with no side effects, is easy to test and reuse. card(stall) is one. Application state is still mutated, deliberately, in one place: Act 3.

Shallow copies

[...stalls] copies the array, not the objects in it: change copy[0].price and stalls[0].price changes too. A deep copy: structuredClone(stalls).

~0:20. Don't go deep on immutability; the rule of thumb is enough: don't change data you were given, return new data. The shallow-copy note is for the curious; structuredClone exists if someone asks.

<template>

The markup stays in HTML

A <template> is parsed but not rendered. Its content is a separate DocumentFragment: document.querySelector("h3") won't match inside it.

HTML owns the structure and the classes the CSS expects; JavaScript only sets the content.

Lecture 4 built a ticket with six createElement calls. For a card with five parts that's 20 lines and the markup is invisible in the HTML. A template keeps the designer's HTML where a designer looks for it. cloneNode(true): true = deep, with all descendants.

A record → a DOM element

card(stall) maps data to an element

textContent for every value: a stall named <img onerror=…> stays text (Lecture 4, XSS lab).
classList.toggle(name, force): adds when true, removes when false. undefined means no force, so it toggles: a missing soldOut key adds the class. Hence Boolean(…).
data-id: maps an element back to its record.

It's a pure-ish function: same stall in, same element out, nothing else touched. You can call it in the console: card(stalls[0]) and see the element.

The whole list

render(): replace all children with new elements

1 · list.map(card)

An array of 8 new <li> elements, not yet in the document.

2 · …spread

replaceChildren(a, b, c) takes separate arguments: spread the array.

3 · replaceChildren

Removes all existing children, appends the new ones. Idempotent: call it twice, still 8 cards.

"Isn't throwing everything away slow?" For 8, 80, 800 cards: no, the browser does this in a millisecond. For 80 000 you'd draw only what's visible, or use a library that compares old and new and only touches what changed. That's what React's "virtual DOM" is: the same idea, smarter. One honest cost: redrawing loses focus and scroll inside the list (mention, don't solve).

Someone will suggest list.innerHTML = stalls.map((s) => `<li>${s.name}</li>`).join(""). Fine for data you typed yourself; for anything a visitor or a server sends, it's XSS (Lecture 4), and without .join("") the array becomes text with commas between the cards. Templates + textContent are safe by default. Demo: playgrounds/xss-lab.html (2 minutes: presets 2 and 5 on the left leak the session token to the attacker's log; the right side doesn't; preset 3 shows why filtering <script> isn't a defence).

The jam, revisited

Where does the UI state live?

Lecture 4: in the DOM

  • The filter: in aria-pressed on five buttons.
  • Shown or not: in hidden on every card, written by two features.
  • Saved: in the ♡'s text.
  • Reads query the DOM; writes patch it in place.

Today: in one object

  • const state = { tag, query, saved }
  • Events write to state. Only state.
  • render() reads state and renders everything: cards, pressed buttons, counts.
  • The DOM can't get out of sync: it's re-rendered from a single source of truth.

The left column isn't wrong for one feature; it's the jam's approach and it worked. It breaks at two features that touch the same elements. The right column is the "source of truth" idea: one place where each fact lives.

State

Minimal state: what can change, not what can be derived

In the state

User input: a tag, a query, a set of ids.

Derived state

The visible stalls, the counts: computed on every render. A stored copy goes stale.

The test for "should this be in state?": could I compute it from what's already there? If yes, compute it. saved stores ids, not elements and not names: elements are thrown away on every render, names can change.

Event → state → render

Events change the state, then render

From here render() takes no argument: it reads state itself. Add search: one key in the state, one filter line, one listener. No conflicting writes to the DOM.

Compare with Lecture 4's filter: there the click handler set aria-pressed and hidden itself. Here the handler is two lines and render draws the buttons too, so they can never show a filter that isn't the current one.

Controlled inputs

render() sets form controls too

While the user types, the input's value and the state agree. They diverge when state changes another way: a "Clear" button, state loaded from storage.

So render() sets every control from state, like the cards. The if: setting the value of a focused input can move the caret.

This is the slide that keeps the promise of slide 21 ("the page can't disagree with itself"). Same for checkboxes: checkbox.checked = state.onlySaved once there is one (Exercise 3's bonus, the homework). Exercise 4's bonus (Clear my night) fails its check without it.

Quick check · after a render

The first click on a ♡ works. The second does nothing. Why?

render() replaced the elements the listeners were attached to. The new buttons have no listeners.
One listener on .vendor-list, which is never redrawn, and event.target.closest(".save"): event delegation, Lecture 4. It handles elements created after the listener was attached.

Same root cause as the jam's "filter can't see the new stall": a list of elements taken once, then the page changed. With render-from-state, delegation isn't an optimisation any more; it's the only thing that works.

~1:43. Today's choice is localStorage: the filter and the saved ids are small, per user, per device, and losing them costs nothing. localStorage

A per-origin key-value store

Synchronous: every call blocks until done. Fine for a few keys, wrong for megabytes.

Strings only. Other values are coerced with String().

Not for passwords or tokens (any script on the page can read it), and not shared between devices. DevTools → Application → Local storage shows and edits it.

Show it live in DevTools on any site you trust, Application tab. sessionStorage has the identical API.

JSON · JavaScript Object Notation

JSON: a language-independent text format

Six types: object, array, string, number, boolean, null.

Stricter than a JS literal: keys and strings in double quotes, no trailing commas, no comments. No undefined, functions, Date, Set, NaN.

Everywhere: web APIs (next week), config files (package.json), storage. Every language has a parser.

Most of them have used JSON; this slide is a one-minute reference for the differences from a JavaScript object literal. JSON.stringify(value, null, 2) pretty-prints. Dates become strings and don't come back as dates; undefined properties are dropped; NaN becomes null.

JSON

Serialising state: stringify and parse

'{"saved":{}}'. A Set serialises to an empty object, silently.
In: [...state.saved], an array. Out: new Set(data.saved).
JSON.parse throws on broken text, and getItem gives null on a first visit. Plan for both.

Predict the last line before revealing. Dates, Maps, functions and undefined don't survive JSON either; arrays, plain objects, strings, numbers, booleans and null do. The bug hunt at the end of the day has its own storage bug.

The whole pattern

Save on every update, load before the first render

Persist user choices, not derived state. The search query is excluded on purpose: it's transient.

Everything from storage is untrusted: it may be missing, from an older version of your code, or edited by hand in DevTools. Exercise 4's checks do all three, by reloading the preview.

One file, everything global

Remember this from the jam?

Uncaught SyntaxError: Identifier 'stalls' has already been declared (at feature.js:1)

Every classic <script> on a page shares one global scope. Two files that both say const stalls collide, and the second file doesn't run at all.

Today's market.js is 200 lines: data, state, storage, rendering, events, the menu, the form, all in the global scope. Every new feature risks a name collision.

Open the starter's market.js on the projector and scroll: the numbered sections are already the seams. Type stalls into the console: it answers, because it's global.

Modules

A module is a file with its own scope

Top-level bindings are private unless exported; dependencies are explicit imports. The browser resolves the import graph and fetches each module.

Like imports in most languages, except the specifier is a URL: relative, with the extension.

The fine print

Four rules for modules in the browser

1 · paths

"./data.js": relative, starting with ./, with the .js. "data" is a 404.

2 · a server

file:// gives a CORS error. Modules need http://: npx live-server.

3 · deferred

Module scripts are deferred by default: they run after the document is parsed.

4 · read-only imports

state = {} in another file fails: "Assignment to constant variable". Change its keys: state.tag = "food".

Also: modules run in strict mode (a typo'd assignment to an undeclared name throws instead of creating a global), and each module runs once, however many files import it. So state is the same object everywhere it's imported: that's what makes the shared state work.

Separation of concerns

One responsibility per module, dependencies in one direction

data.js

The data.

state.js

State and derived state.

storage.js

Persistence.

render.js

Rendering.

main.js

The entry point. Attaches the event listeners: each handler updates state, then calls update().

main → render, storage, state · render → state, data · storage → state · state → data

The direction matters more than the number of files: data knows nothing, state knows data, render knows state, main knows everyone. If render.js ever needs to import main.js, something is in the wrong file. Next week mostly touches data.js and the start-up in main.js.

Breakpoints

Four kinds of breakpoint

HowStops when
Click a line numberthat line is about to run
debugger; in your codethat line runs, while DevTools is open
Event Listener Breakpoints → Mouse → clickany click handler runs: useful when you don't know which code handles it
Breakpoints → Pause on caught exceptionsan exception is thrown, even one a try … catch swallows

The event-listener breakpoint is the one to remember for other people's code: click the button, DevTools stops inside whatever handles it. "Pause on caught exceptions" finds errors a try … catch swallows, like a load() that falls back to the defaults without saying why. Conditional breakpoints (right-click a line number) are in the cheat sheet.

A method

Debugging is testing hypotheses, one at a time

  1. Reproduce it. Write the steps down: "click Food, then All".
  2. Hypothesise: which function produces the wrong result? (A handler? State? Render?)
  3. Set a breakpoint there and reproduce again.
  4. Inspect: is the state what you expected? Scope, Watch, hover a variable.
  5. Step until an actual value differs from the expected one. That line is the bug.
  6. Fix, then repeat step 1 to verify.

With state and rendering separated, step 2 narrows quickly: wrong state → the event handlers. correct state, wrong DOM → render.

The payoff of today's structure for debugging: the bug is either in "what changed the state" or in "how the state is drawn", and you can tell which by pausing in render and looking at state.
