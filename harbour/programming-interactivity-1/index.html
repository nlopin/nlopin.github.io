02

Where HTML came from

HTML isn't a fixed thing you memorize once. It has changed shape completely at least twice, and today it doesn't even have a version number. That history explains a lot of the web's weirdness — including some of what you just saw in the opening tour.

Timeline — click an era

Today the spec lives at html.spec.whatwg.org, maintained by the WHATWG — a group steered by Google, Mozilla, Apple, and Microsoft, with anyone free to file an issue or open a pull request against it on GitHub. A change generally needs two independent browser engines willing to actually implement it before it's considered settled. There's no vote, no fixed release date, and no "HTML6" planned — it just changes, in public, constantly. That's why it's called a Living Standard rather than a numbered spec.

Live demo — the spec's actual commit history

Don't take "living" on faith — this fetches the real, current commit log of the WHATWG HTML spec's source repository.

Talking point

The throughline: who gets to decide what a browser must do? First nobody (browser wars), then a slow committee that bet wrong (W3C/XHTML2), then the vendors who actually ship browsers took it back over (WHATWG). Worth naming that this is a genuine case study in open-source governance, not just trivia.

03

The web platform: what's in the box

HTML is the document format. But a modern browser is really more like an operating system: it hands JavaScript access to dozens of capabilities that have nothing to do with markup. These are all just functions you call — no plugin, no install, no special syntax. You've already used three of them on this page without noticing.

Fetch used above ↑

Make an HTTP request from JavaScript, read the response as text or JSON.

DOM used above ↑

Read and change the tree of the page itself, live, while it's running.

Web Speech used below ↓

Text-to-speech and speech-to-text, built into the browser.

Canvas / WebGL / WebGPU

Draw pixels and 3D graphics directly, frame by frame.

Web Audio

Generate, analyze, and mix sound in real time.

Geolocation & sensors

Ask (with permission) for location, device orientation, motion.

Storage

localStorage and IndexedDB: save data on the visitor's machine, no server needed.

WebSockets

Keep a connection open so server and client can push messages either way, anytime.

WebRTC

Peer-to-peer audio, video, and data — straight between two browsers.

Service Workers

Intercept network requests, cache assets, work offline, send push notifications.

Web Workers & WebAssembly

Run real computation off the main thread, or run compiled non-JS code at near-native speed.

Media capture & files

Read the camera, microphone, dropped files, or the clipboard, with the user's OK.

Not all of these come from the same standards body — WebGL comes from the Khronos Group, WebRTC is jointly W3C and IETF, most of the rest are W3C or WHATWG working groups. In practice you won't read any of those specs day to day; you'll live in MDN's Web API index and check caniuse.com before relying on something new.

Talking point

This is the "wow" moment to spend a beat on: the useless-web-button, the 3D portfolio game, and the text-to-speech demo they just heard are all built from this same list, called from plain JavaScript. Nothing here needs a framework. Good moment to preview that the rest of the course is essentially "learning to call these."

What just happened, in order: your browser opened a connection, sent a plain-text HTTP request with a method and headers, the server ran some code and sent back a plain-text HTTP response (status code, headers, body), and only then did the browser do anything with it. A server doesn't know or care what a "webpage" looks like — it just sends bytes.

Talking point

Emphasize the response is just text — status line, headers, body. Nothing about fonts, layout, or color exists yet. Rendering is a separate step the browser does afterward. If wifi fails, open the Network tab live instead (bridges into section 8).

A destination with no screen at all

A screen reader is a browser too — it just turns the DOM into speech instead of pixels. Click below to hear this page's own text read aloud, using your browser's built-in speech engine (no server involved this time — it's entirely local).

Live demo — text to speech

A screen reader doesn't see color, spacing, or a hero image. It reads the DOM, in document order, using whatever semantic information the HTML provides — headings, lists, button labels, alt text.

Talking point

Ask: "what did the speech engine skip?" (Nothing here — it's plain text.) Now imagine the sentence were an image with no alt — the screen reader destination gets nothing. Same document, different destinations, wildly different experiences if you don't plan for it.

07

Your first HTML file, by hand, no tools

This playground is a warm-up. For the real exercise, everyone opens a plain text editor (TextEdit in plain-text mode, Notepad, or VS Code with no extensions) and a browser, saves a file called index.html, and opens it with File → Open. No server, no framework, no npm — just a file and a browser.

Suggested build order (say it out loud as they type)
  1. <!DOCTYPE html> — tells the browser "this is HTML, use modern rules."
  2. <html><head></head><body></body></html> — the skeleton every page has.
  3. A <title> inside <head> — ask them to check the browser tab.
  4. One <h1> and one <p> in <body> — save, reload, see it appear.
  5. An <img> with a deliberately wrong src — reload, see it break, talk about why (bridges into section 8).

Talking point

Land the big idea: everything students just did — editing styles, toggling attributes, reading network traffic — changes nothing on the actual server. DevTools edits a local copy of the tree. Reload and it's gone. That's freedom to experiment without fear, and it's the whole reason "view source" is such a good teacher.

·

Recap

  • A webpage is bytes over a network, sent by a server, interpreted by a client.
  • The same document reaches very different destinations — screens of every size, and no screen at all.
  • The browser doesn't work with your HTML text; it works with the DOM, a tree it builds and keeps valid.
  • You can build a real webpage with a text editor and nothing else.
  • DevTools lets you see and safely break that tree, live, with zero risk to the real file.
