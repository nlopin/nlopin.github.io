Every box is placed by one layout algorithm. The parent's display and the box's own position pick which. One question every act: who decides the width?

This is the spine of the lecture. Flow is not "no layout": it's the default layout algorithm, and it has rules. Position, flex and grid are three more algorithms. The same property (width, margin: auto, z-index) behaves differently depending on which algorithm is in charge.

Deeper · CSS Sizing · the vocabulary for the rest of today

Every box knows two sizes of its own

fit-content = min(max-content, max(min-content, available)) — the “shrink-to-fit” width of absolute boxes, inline-blocks and floats. Flex items start at max-content and shrink to a min-content floor; auto grid tracks sit between min- and max-content.

~3 min. Drag the width down: .c overflows (it refuses to wrap), .b never changes, .d tracks max-content until the space runs out, then wraps like auto. This is the vocabulary for every "who decides the width?" answer today: flow blocks are extrinsic (the container decides), everything else starts intrinsic (the content decides) and then gets stretched or squeezed.

Precise: flex items with flex-basis: auto/content start from max-content (Flexbox §9.2) and are floored by the automatic minimum; auto tracks resolve between a min-content-based minimum and max-content, then stretch (Grid §12). Spec: CSS Box Sizing 3 (min-content / max-content / fit-content). Also usable in tracks: grid-template-columns: max-content 1fr (the form in Ex 4), fit-content(20ch).

Limits · width and height

Set limits, not sizes: min- and max-

  • max-width: grow with the space, but stop here. The readable column, the image that never overflows (max-width: 100%).
  • min-width: shrink with the space, but never below this. Same pair for height: min-height, max-height.
  • Conflict? min beats max beats width. Shortcut: width: clamp(20rem, 50%, 36rem).

~2 min. Drag the window width. Around 900px: 50% would be 434, under the max → 434. Wider than ~900: 50% passes 448 → capped at 448 (max wins over width). Narrower than ~580: 50% drops under 288 → held at 288 (min wins). Below ~320 the card overflows the window: that is the price of min-width.

Why limits instead of sizes: a fixed width breaks on the screen you didn't test. Limits let the box adapt and only say "not narrower than, not wider than". Heights: remember "height grows up" — min-height (the hero, 100vh) is safe, a fixed height cuts content off. Precedence rule (CSS 2.2 §10.4): compute width, clamp to max, then clamp to min — so min wins a conflict. clamp(MIN, VAL, MAX) = max(MIN, min(VAL, MAX)), handy for fluid font sizes too.

The most common layout on the web · drag the window

Leftover space goes somewhere

  • By default margins are 0: the box sits at the left, and all the leftover ends up on the right (the end side).
  • An auto margin claims the leftover. On one side it pushes the box away: margin-left: auto → right.
  • On both sides it splits the leftover in two: margin-inline: auto → centred. With max-width, the classic column.

~2 min. The hatched background is the leftover space. Start as is: max-width caps the box, it sits on the left, the leftover is all on the right. Why: in flow, margin + border + padding + width + padding + border + margin must add up to the parent's width; with fixed margins that can't work, so the browser lets the end margin (the right, in left-to-right text) absorb the difference (CSS 2.2 §10.3.3).

Uncomment margin-left: auto: the left margin claims everything → box on the right. Swap for margin-inline: auto (the modern left + right): split in two → centred. Drag the window: it stays centred at every width, and shrinks on narrow screens because it is max-width, not width. This is the "text runs from edge to edge" fix and step 1 of the showcase.

In flow this only works sideways: height grows from content, so there is never leftover height. Don't explain the vertical case yet — it's the break mystery; in a flex column the same margin-top: auto pushes the link down.

trap 1 · sideways scroll

Width is the content: 100% + 40px.

trap 2 · margin collapse

Adjacent vertical margins collapse: max, not sum (with negatives: biggest positive + most negative). 30. And a first child's margin leaks through a parent with no padding/border.

the mechanism · BFC

Collapsing happens inside one block formatting context. Start a new one and nothing collapses through it. So do flex and grid containers.

Sticky, precisely: it sticks relative to its nearest scroll container (any ancestor with overflow other than visible/clip), and it can never leave its containing block. That is why an ancestor with overflow: hidden breaks it. Modern names: inset: 0 = top/right/bottom/left; logical inset-inline-start follows the writing direction (flips in RTL). "Positioned" = anything except static. "Out of the flow" = the others close the gap, as if it weren't there. Don't explain every row now: the next slides take one value each, and the lab puts them side by side.

position · 1 of 5 · the default

static: just the flow

  • Every element starts here. The box sits where normal flow puts it.
  • top, right, bottom, left are ignored. So is z-index (except on flex/grid items).
  • Not an anchor: absolute children look past it.

~1 min. Change the offsets: nothing happens. Then change static to relative: now they work. That is the whole difference between "static" and "positioned". You rarely write position: static; you use it to undo a position inherited from a framework or a media query.

position · 2 of 5

relative: move it, keep its seat

  • Stays in the flow. Offsets nudge it from where it would have been.
  • The space it left stays reserved: nothing around it moves.
  • Its real job: an anchor for absolute children (with no offsets it moves nothing).

~1.5 min. Change the numbers: the badge moves, the text after it doesn't budge — there is a hole where the badge "should" be. Offsets are relative to its own seat: top: -10px = up. Real use: tiny nudges (an icon 1px down), and mostly position: relative with no offsets on a parent, so absolute children measure from it. Also: a relative element with a z-index creates a stacking context.

Precisely (CSS Position 3): the containing block of an absolute box is the padding box of the nearest ancestor that is positioned or has a transform/filter/perspective/contain/will-change of those. Overlap: who's painted on top?

  • Among boxes of the same kind, later in the HTML paints on top: .c covers .b covers .a.
  • Positioned boxes paint above normal ones — even when the normal one comes later.
  • No CSS needed for any of this: it is the default paint order.

z-index · 2 of 3

z-index: bring one forward

  • Only works on positioned elements (and flex/grid items). On a normal block it does nothing.
  • Default auto. Bigger number = closer to you. A tie → HTML order decides.
  • Negative values go behind the normal content of the page.

~1.5 min. .a jumps to the front with just 2 — the others are auto. .flyer { z-index: 99 } does nothing: it is not positioned. Add position: relative to it and 99 works. Uncomment .c { z-index: -1 }: it drops behind everything, even the page background of its stacking context. Habit: small numbers (1, 2, 10), not 9999 — and the next slide shows why even 9999 can lose.

z-index · 3 of 3 · deeper · stacking contexts

Why z-index: 9999 loses to 10

A stacking context seals its children into one layer: transform, filter, opacity < 1, isolation: isolate, position: fixed/sticky, a positioned element or flex/grid item with a z-index, container-type… Inside, 9999 is huge; outside, the whole layer sits at 0 — below 10.

~2.5 min (slides 26–27 set it up). The dropdown pokes up over the header's edge — and is painted under it. The card is position: relative (base) and has a transform, so the card is a stacking context at level 0/auto. The dropdown's 9999 only ranks it among the card's children; the whole card paints below the header's 10. Fix A: delete the transform — the card stops being a context (positioned, no z-index), the dropdown's 9999 now competes at the root and wins. Nothing moves: only stacking changes. Fix B: keep the transform, lift the context: .card { z-index: 11 }.

Paint order inside a context (CSS 2.2 Appendix E, simplified): background → negative z → in-flow blocks → floats → inline content → z-index auto/0 positioned (DOM order) → positive z. Contexts are not directly visible in DevTools (Chrome's Layers panel shows compositing layers, a different set); Edge's 3D View in z-index mode comes closest. For components: isolation: isolate on the root keeps internal z-indexes local.

Deeper · the #1 flex bug in production

Why won't it truncate?

The flex item is .info, and flex items default to min-width: auto = their min-content. Its nowrap title makes that the whole sentence, so .info refuses to shrink and shoves the button out. min-width: 0 on the item removes the floor.

~3 min. At 620px the Menu button is pushed half out of the card (drag narrower and it leaves the view entirely). Ask: "the h3 has overflow hidden and ellipsis — why no ellipsis?" Because the h3 is never narrower than its text: its parent, the flex item, won't shrink below the h3's min-content. Uncomment min-width: 0: ellipsis. Drag the width.

Spec detail (Flexbox §4.5): the automatic minimum only applies to flex items that are not scroll containers — so overflow: hidden on the item itself would also fix it (but clips focus rings and shadows). Habit: min-width: 0 on flex items that hold text you truncate, long URLs or code.

Live · the purple lines are what DevTools draws

Columns, rows, and the fr unit

fr = a share of the leftover space, after fixed tracks and gaps (flex-grow for columns). But 1fr is really minmax(auto, 1fr): never below its content.

Blowout demo: uncomment the long word: the 1fr column grows, the ratios break. 1fr = minmax(auto, 1fr), and auto as a minimum means min-content (Grid §7.2.4). Fix with minmax(0, 1fr) (and then handle overflow: overflow-wrap: anywhere). Track sizing algorithm (Grid §12), in one breath: fixed tracks first, then intrinsic tracks get their content sizes, then leftover goes to fr tracks.

First point out: we never wrote any rows, yet there are two — grid makes rows as needed ("implicit" rows, as tall as their content). Items fill cells left to right, top to bottom.

Then try: 1fr 1fr 1fr → repeat(3, 1fr) → repeat(4, 1fr) → add grid-template-rows: 100px 50px: now the rows are "explicit", with the sizes you chose.

Last time I promised · three steps

Decode the magic line

grid-template-columns:
  repeat(auto-fill, minmax(16rem, 1fr));
minmax(16rem, 1fr) · one column: never narrower than 16rem, and takes a share of what's left
repeat(auto-fill, …) · as many of those columns as fit in the row
Wide screen → more columns. Phone → one. Responsive, without a media query. auto-fit collapses empty tracks, so 2 items on a wide screen stretch; auto-fill keeps the empty columns.

The payoff. Everyone pasted this line last time as "layout magic". Read it inside out. auto-fit vs auto-fill: only differ when there are fewer items than columns (auto-fit collapses the empty tracks, so items stretch). Next slide: watch it.

Deeper · the wobbly links, solved at the grid level

subgrid: children line up across cards

Each card spans 4 rows of the outer grid and uses those rows for its own children. Now every title, every text and every link shares one row line across all cards. Flex could only push the links down.

Who decides the width? · grid items

The track decides. The item stretches.

By default a grid item stretches to its cell, both ways — and a stretched item has a definite height, so height: 100% inside it finally works (the payoff from “height grows up”). justify-items / align-items give the size back to the content. place-items: center = both at once: the famous two-line centring.

Closing the loop from Act 1: a stretched flex or grid item is treated as definite (Flexbox §9.8, Grid §11.5 / CSS Sizing), so percentage heights of its children resolve. That is why "make the child fill the card" suddenly works inside flex/grid.

Read the blue labels: every item is exactly its track wide and its row tall. Uncomment justify-items: start: the widths shrink to the content. Then align-items: start: the heights too. Then only place-items: center. Fourth answer to the question of the day: the track decides, unless you hand it back to the content.
