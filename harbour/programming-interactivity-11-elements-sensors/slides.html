Quick check · in the console

What did the parser make of them?

HTMLElement with a hyphen, HTMLUnknownElement without.
A name with a hyphen is a valid custom element name: reserved for authors, so no future HTML element can take it. It must start with a lowercase letter.

~0:06. The parser keeps unknown tags in the tree with their attributes and children; they behave like a <span> (display inline). HTML has added elements over the years (<dialog>, <search>), none with a hyphen, and the spec promises it never will. A few hyphenated names are reserved because SVG and MathML use them (font-face, annotation-xml). Convention: a prefix for your project or library (gh-, sl-), so two libraries don't collide.

Step 2 · demos/green-room/02-define

An element is a class with a tag name

  • extends HTMLElement: this is the element itself, with every DOM method.
  • customElements is the page's registry: name → class.
  • From now on the parser, createElement and innerHTML all create a LevelMeter.
  • connectedCallback: the browser calls it when the element enters the document (Lecture 4: you don't call it, the browser does).

~0:07. Step 2 develops the meter alone on a bench page, with its own level-meter.css (classes .bar, .bar.on). That file comes back as a problem in step 4. replaceChildren, not append: the element can be connected more than once (moved, re-inserted), and appending would add ten more bars each time.

The order doesn't matter

Tags parsed before the definition get upgraded

// before define: an HTMLElement, no behaviour
document.querySelector("level-meter")
  .constructor.name          // "HTMLElement"

// after define: the same object, upgraded
  .constructor.name          // "LevelMeter"

await customElements.whenDefined("level-meter");
  • Script in the <head>, at the end of the body, defer, a module, import() later: all work.
  • :defined / :not(:defined) in CSS: style the moment before the upgrade, so nothing jumps.
  • whenDefined: wait for it in code.

~0:09. Trap worth knowing: if the page sets a property before the upgrade (meter.value = 0.5 on the plain HTMLElement), that creates an own property on the object, which later hides the class's setter. Robust elements check for it in connectedCallback: read the own property, delete it, and assign it again so it goes through the setter. Lit does this for you. In the demo, module scripts run in document order, so the definitions always come first.

~0:10. Moving an element with appendChild calls disconnected then connected. On upgrade, attributeChangedCallback runs once for each observed attribute already in the markup, before connectedCallback. disconnectedCallback gets one line today and becomes the climax of Act 2.

Quick check · two ways to create the same element

What does the constructor see?

From markup: "20". From createElement: null: the attributes don't exist yet.
createElement also fails: "The result must not have children". The constructor may not add attributes or children. Read and render in connectedCallback.

~0:11. Predict first. Chrome reports the error in the console and hands back an element that doesn't work. Exact message: NotSupportedError: Failed to execute 'createElement' on 'Document': The result must not have children (or "attributes"). The spec forbids it because createElement promises an empty element. Attaching a shadow root in the constructor is fine: it isn't a child.

Step 3 · demos/green-room/03-attributes

Observed attributes configure the element

  • Only names in observedAttributes trigger the callback: the browser doesn't call you for every class change.
  • Values arrive as strings, or null when removed.

~0:12. In the console: meter.setAttribute("value", 0.8), the bars jump. #build is a private method (#): not reachable from outside the class, so the page can't depend on it. The isConnected check matters for createElement + setAttribute before the element is inserted. When tags in the page are upgraded, they're already connected, so bars builds once in the callback and again in connectedCallback: harmless, because #build replaces the children.

Quick check · in the console

meter.value = 0.8. Nothing happens. Why?

An attribute is a string in the markup. A property is a field on the object. Nothing connects them until you write the getter and setter.
Like <input>: the value attribute is the starting value, the value property is the current one. Setting the property doesn't rewrite the attribute.

~0:13. Without the setter, meter.value = 0.8 creates a plain field and the display ignores it. Check the <input> analogy live: type into any input, then compare input.value with input.getAttribute("value"). The fake slider in step 3 drives the property, up to 60 times a second.

Step 5 · demos/green-room/05-shadow

A shadow root: a DOM tree only the element sees

<level-meter>   ← the host
  #shadow-root (open)
    <style>     ← inside only
    <span class="bar">
    <span class="bar">
    …
</level-meter>

~0:18. The page's .bar doesn't match inside; the shadow root's .bar doesn't match outside. document.querySelector(".bar") no longer finds the meter's spans. mode: "open" exposes element.shadowRoot for debugging and tests; "closed" returns null there, but it isn't security: anyone can patch attachShadow before your code runs. Native elements use the same mechanism: tick "Show user agent shadow DOM" in DevTools settings and inspect an <input type="range">. One template, cloned per instance: the markup is parsed once.

Encapsulated, not isolated

What crosses into a shadow root, and what doesn't

from the pagecrosses?
selectors: .bar, span, level-meter spanno
inherited properties: color, font, line-heightyes, through the host
custom properties: --meter-coloryes: they inherit too
::part(bar)only what the element marks with part="…"
document.querySelectorno: it stops at the host

~0:20. That's why the meter's text would still use the app's font: inheritance flows down the flat tree. :host { all: initial; } cuts even that, rarely what you want. Global styles that should reach in (a reset, a design system) need to be adopted into the shadow root explicitly (shadowRoot.adoptedStyleSheets).

ElementInternals

A form-associated element talks to its form like a native control

  • setFormValue: what FormData gets under the element's name.
  • setValidity: the same flags as input.validity; the form won't submit while one is true.
  • Lifecycle for forms: formResetCallback, formDisabledCallback, formStateRestoreCallback.
  • It's labelable: <label for="mic"> works.

~0:28. Also expose what a native control exposes, delegated to the internals: form, name, validity, validationMessage, checkValidity(), reportValidity() (all in 07-form/device-picker.js). :invalid and :user-invalid match the element. Now submit with nothing picked: the form refuses, but no message appears, and the console says An invalid form control with name='mic' is not focusable. That is the next problem.

The element reports, the page decides

Events out, and what happens at the shadow boundary

  • Events from inside are retargeted: outside, event.target is the host. The inside stays private.
  • composed: false (the default for your events): the event stops at the shadow root.
  • event.composedPath() lists the whole path, for debugging (open roots only).

~0:30. Built-in UI events (click, input, keydown) are already composed. Name your events after what happened (change, pick, statechange), not after what the page should do. Dispatching on the host is usually the simplest: bubbles but no composed needed, and event.target is the element either way. A change on the picker reaches the form's change listener, like a native control's.

Judgement

When a custom element is the wrong tool

  • A native element does the job: <dialog>, <details>, popover, <select>, <input type="range">. You'd rebuild their focus, keys and semantics, worse.
  • It's only layout: a <two-columns> wrapper is a CSS class.
  • It's used once, and has no state or behaviour of its own.
  • The content belongs to the page (its text, its translations, its styles) but you'd render it inside a shadow root: use slots, or no shadow root.

Good candidates: a widget with state and behaviour that several pages or apps share, like the three in the green room.

~0:36. The green room's picker is a teaching vehicle: it shows form association, focus and roles in one element. In production, this exact picker would be a styled <select>; a custom one pays off when it shows what <select> can't, like a live level per microphone. Not covered: customised built-ins (<button is="fancy-button">, extends HTMLButtonElement) keep a native element's behaviour, but Safari has declined to implement them; autonomous elements plus ElementInternals are the portable route. A custom element without a shadow root is fine and common (GitHub's are mostly light DOM): the app's styles apply, and the class still gives you a lifecycle. The green room itself becomes one in step 11.

Step 9 · the green room on a phone, over plain HTTP

On http://192.168…, the API isn't there

// laptop, http://localhost:8080        navigator.mediaDevices   // MediaDevices {…}
// phone,  http://192.168.1.20:8080     navigator.mediaDevices   // undefined
                                       window.isSecureContext   // false
  • A secure context: HTTPS, or localhost / 127.0.0.1. Camera, microphone, motion sensors, geolocation, the clipboard, service workers work only there.
  • No prompt: the property is missing (mediaDevices), or it exists and every call fails (geolocation). Check isSecureContext and say why.
  • To test on a phone: deploy (GitHub Pages is HTTPS), or a tunnel, or DevTools → Sensors on the laptop.

~1:01. The first gate, before any prompt. The reason: on plain HTTP anyone on the network can change the page, and a page that can switch on your camera mustn't be editable by the café's Wi-Fi. 09-microphone/main.js's setup() checks first and disables the button with a sentence that names the origin.

One call, one prompt

getUserMedia asks for a stream

  • A MediaStream holds tracks, one per source. A <video> plays it: video.srcObject = stream.
  • Constraints: which device, which size; exact fails if it can't be met.
  • The first call shows the prompt. A promise: it waits as long as the user does.

~1:02. Asking for { audio: true, video: true } in one call gives one combined prompt; the green room asks in two calls from one click (the preview asks for video, the page for audio). Chrome shows them together or one after the other; Firefox shows two.

Live, in Chrome · "Never allow", then try again

After a block, the page can't ask again. Only the user can undo it.

  • Chrome: call getUserMedia again, or reload: instant NotAllowedError, no prompt.
  • Firefox keeps a block for the session unless "Remember" was ticked; Safari asks again on a later visit. Code for the strictest case.
  • The user resets it in the site controls next to the address bar, or in the browser's settings.
  • So the blocked message says where to click, not "please allow".
consequence

A prompt on page load, before the user knows why, gets blocked by reflex. And that block is permanent. A careless prompt is a feature lost for good on that site.

~1:04. Do it live in 09-microphone: "Never allow", click again, reload. Then reset through the site controls (the icon left of the URL in Chrome → Reset permissions). Browsers also hide or auto-block prompts that aren't tied to a user action, most visibly for notifications (Chrome's quiet permission UI).

Read the state, then ask

Choose the screen before anything is asked

  • permissions.query reads the state without a prompt.
  • prompt: explain first, then a button; the browser asks after the click.
  • denied: skip the button, show how to reset.
  • Permission names differ between browsers: always try.

~1:05. Every real call app does this: a screen that says what it needs and why, then the system prompt. The "unknown" branch behaves like "prompt". Lecture 10's "Plan for no" slide was the same idea for geolocation.

Yesterday's yes is not today's

A grant can be one-time, and it can be taken back mid-call

  • Chrome offers "Allow this time"; Firefox remembers only if the user ticks a box; Safari asks again in later visits.
  • The user can revoke access in the site controls while the camera runs.
  • Listen to both the permission (change) and the track (ended).

~1:06. So the page can't store "the user said yes" in localStorage and skip the checks next time. Step 12 adds both: the preview watches the camera permission itself (it switches to blocked) and its track (failed); the green room watches the microphone. Revoke the camera in the site controls while it runs: the preview shows its blocked message. ended fires when the source stops on its own, never because your code called stop().

demos/green-room/09-microphone/autoplay.html

An AudioContext created on load. What's its state?

"suspended", then "running" after the click. The autoplay policy: no sound before the user has interacted.
Another gate: user activation. No prompt, no setting: the browser tracks clicks, taps and key presses. getUserMedia doesn't need it; the meter's AudioContext does, so create it inside the click.

~1:07. Open the autoplay page in a fresh tab without touching it. Chrome also warns: "The AudioContext was not allowed to start. It must be resumed (or created) after a user gesture on the page." navigator.userActivation.hasBeenActive is sticky activation (any interaction so far, enough for audio); isActive is transient activation (an interaction in the last few seconds, needed for fullscreen, pop-ups, EyeDropper and, in Firefox and Safari, clipboard writes). An await before the call can use up the transient window.

Trap · the prompt resolves after the world moved on

A stream can arrive after you stopped wanting it

  • The user clicks Back while the prompt is open: disconnectedCallback runs first, the stream arrives after.
  • Two quick picks in the device list: two calls in flight, the first stream overwritten and never stopped.
  • After every await, check whether the answer is still wanted.

Trap · same scene

Moving an element disconnects it first

  • append to a new parent: disconnected, then connected.
  • moveBefore() keeps the element's state (and a playing video) and calls connectedMoveCallback instead.
  • Where it isn't supported: make restarting cheap, or move the element less.

~1:18. moveBefore shipped in Chrome 133 (2025). Feature-detect it: "moveBefore" in Element.prototype, and fall back to append. 12-cleanup/camera-preview.js defines an empty connectedMoveCallback, which is enough: defining it means "a move isn't a disconnect for me". Step 13 · demos/green-room/13-embedded

The page that embeds you decides what you may ask for

  • Permissions Policy: checked before any prompt. By default camera and microphone are allowed for the page's own origin only.
  • A cross-origin frame needs allow to use it at all. Chrome then asks on behalf of the top-level page: the prompt names it, and the grant is stored for it.
  • The header turns a feature off for a page and its third-party scripts.

~1:19. Open 13-embedded on localhost: frames A and B load from 127.0.0.1, another origin. A says "doesn't allow", B can use the camera, C (same origin, 'none') is refused. B's prompt names localhost, the top-level page: if the camera is already allowed or blocked for localhost from earlier steps, B follows that without asking. Reset permissions before this step. The frame reads its policy with document.featurePolicy.allowsFeature("camera") in Chromium; elsewhere getUserMedia just fails with NotAllowedError. On GitHub Pages you can't set response headers; other static hosts (Netlify, Cloudflare Pages) read them from a _headers file.

What the green room's three tags have in common

The contract for every tag in the jam

  1. One module defines one element. Drop the file into any page and the tag works.
  2. Attributes configure, properties carry live data, events report. The page never reaches into the shadow root.
  3. Gates in order: nothing starts before a gesture; read the permission state, ask only when the user asks for the feature.
  4. Handles no with visible content that says how to undo it, and notices a revoke.
  5. Releases everything in disconnectedCallback.

For any element you write

Three questions before you ship a tag

  1. What does it expose: attributes, properties, events, parts, custom properties?
  2. What does it acquire, and where does it release it?
  3. Which gates does it pass, and what does the user see when one says no?
