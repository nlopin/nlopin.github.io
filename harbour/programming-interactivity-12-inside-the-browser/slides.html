The whole lecture in one sentence

A browser is a set of processes and threads. Knowing which one does what explains both speed and safety.

Every loading problem is one stage waiting on another. Every frontend attack is someone else's code or request acting with your origin's rights.

Chrome 67, 2018 · after Spectre

Sites never share a renderer, and a frame counts separately

// news.example/article
<iframe src="https://ads.example/banner">

Task Manager:
  Tab: Today's news        renderer A
  Subframe: ads.example    renderer B
  • A cross-site iframe gets its own process, so its memory never sits next to yours.
  • Spectre showed that code can read any memory in its own process, whatever the language-level checks. The fix was to stop putting two sites in one process.
  • A crashed or frozen renderer takes down one site's frames, not the browser.
  • "Site", not origin: a.news.example and b.news.example can share a process.

~0:07. Spectre (January 2018) was a CPU bug: speculative execution left timing traces that let code read memory it shouldn't. No software fix inside a process was reliable, so Chrome made the process boundary the security boundary and shipped site isolation for desktop in Chrome 67. The cost is memory, which is why mobile got it later and only for sites you log into. Two consequences we use later: a hostile iframe can't read your memory, and SharedArrayBuffer / high-resolution timers need extra headers (COOP/COEP) to come back.

~0:09. This table is the spine of Act 2: every stage we open belongs to one of these rows. Name the demo again — box 2 kept moving because it never needed row 1. Why a page has to ask

A renderer can't touch the disk, the network or the camera

// in the page's renderer
fetch("/api/articles")
   → IPC → network service
     (a loader locked to this origin)

navigator.mediaDevices.getUserMedia(…)
   → IPC → browser process → prompt → OS
  • The renderer process runs with almost no OS rights: no file access, no sockets, no devices.
  • Everything goes over IPC to a more privileged process, which checks it first.
  • That check is where the permission prompts of Lecture 11 and the origin rules of Lecture 8 are enforced.
  • A bug in the renderer is not yet a compromised machine: an attacker also needs a sandbox escape.

~0:11. Useful model for the second half: page code can only send requests over IPC, and the browser process decides what each request may do, so "the client holds no secrets" (Meridian) and "the user's cookies travel with the request" are both decisions made out there, not in the page. Chrome pays bug bounties in two tiers for this reason: renderer RCE alone is worth less than a full chain with a sandbox escape.

Loading · the article page

Parsing starts long before the last byte

// browser process + network service
DNS      news.example  → 93.184.…
TCP      handshake
TLS      handshake
GET /article/42
         … time to first byte …

// the response body streams in, in chunks
<!doctype html><html><head><link …   chunk 1
<p>The council voted …                 chunk 2
  • The navigation happens in the browser process; the response is handed to a renderer.
  • HTML is parsed incrementally: the first chunk builds DOM while the rest is still in flight.
  • A server that assembles the whole page before sending (and then sends it at once) throws that away.
  • The renderer may be reused or swapped: a cross-site navigation gets a fresh process.

~0:16. The practical consequence of streaming: send the <head> early. A server that flushes the head while the database query is still running lets the browser start fetching the stylesheet and the font during that query. That is what "streaming SSR" and the newer 103 Early Hints status are about. In the Network panel, the green "waiting (TTFB)" bar is the part before chunk 1 and the blue bar is the streaming part.

One slow script in the head costs you the whole page

A classic <script> blocks parsing until it has run

<script src> classic
parsefetch — parser stoppedrunparse
<script defer>
parse (fetch in parallel)runDOMContentLoaded
<script async>

  • defer: after parsing, in document order, before DOMContentLoaded.
  • async: the moment it arrives — any order, may interrupt parsing.
  • Modules are deferred by default; async works on them too.

~0:20. Mental rule: defer for your own code that needs the DOM, async only for something standalone that nothing else depends on (an analytics beacon). Inline <script> without src blocks too — and it also waits for any stylesheet already requested, because it might read computed styles. document.write in a script is the worst case: the parser has to splice new bytes into the stream it is already parsing.

~0:22. Have someone commit to an order before revealing. Worth adding: async is a race, so two async scripts that depend on each other break intermittently — the classic "works on my machine, fails on a slow connection" bug. The inline script in the body runs when the parser reaches it, which is why "put your script at the end of the body" worked before defer existed.

A second parser, looking ahead

While one parser is blocked, a second one fetches ahead

// the main parser stops here
<script src="analytics.js"></script>

// the preload scanner reads ahead and
// starts these anyway:
<link rel="stylesheet" href="article.css">
<img src="hero.jpg">
<script src="comments.js" defer></script>
// invisible to it: URLs built at runtime
hero.src = "/img/hero-" + width + ".jpg";
new Image().src = pickHero();
  • It scans raw bytes for URLs in src and href and queues the fetches early.
  • It is the reason a blocking script hurts less than it should — and the reason a JavaScript-built URL is always late.
  • CSS background-image is late too: the URL is only known after the stylesheet is parsed and the element is styled.
  • Fix: put the real URL in the HTML (<img>, srcset) or declare it with <link rel="preload">.

~0:24. This is the single most common cause of a slow LCP on an otherwise fine page: the hero image is chosen by a script, so it is discovered a second after everything else. Show it in the Network panel waterfall — the image request starts after the script's. Lazy-loading the hero (loading="lazy" on the first image) has the same effect and is a frequent accident.

Why the screen stays blank

No first paint until the <head> stylesheets arrive

// render-blocking
<link rel="stylesheet" href="article.css">

// not render-blocking: a condition that is false
<link rel="stylesheet" href="print.css"
      media="print">

// a script waits for the stylesheets before it
<link rel="stylesheet" href="slow.css">
<script>el.offsetHeight</script>  // must wait
A stylesheet in the body blocks everything after it.
  • Painting unstyled content and restyling it would flash, so the browser waits.
  • A script may read computed styles, so it waits for pending stylesheets too — a slow CSS file delays your JavaScript.
  • media that doesn't match downloads at low priority and doesn't block.
  • Fonts don't block the first paint; they decide what the text looks like, and can shift it.

~0:26. Demo if there is time: throttle to the 3G preset and watch the white screen for the length of the CSS download. Two numbers worth knowing: a blocking stylesheet on the critical path costs one full round trip, and splitting CSS per route usually beats inlining everything. Modern alternative to the media trick: blocking="render" makes blocking explicit for other elements, but the default for <head> stylesheets stays as described.

Stage 2 · from rules to computed styles

Every property of every element gets a value

// matching: right to left
.article p > strong { … }
       ↑ start here: is it a strong?
       then: is the parent a p?
       then: is an ancestor .article?

// the result, per element
getComputedStyle(el).color  // "rgb(23, 20, 15)"
  — no property is ever "unset" here
  • Selectors are matched right to left: the browser starts from the element, so a long descendant chain is cheap to reject.
  • The cascade, inheritance and defaults resolve every property into a computed style per element.
  • Invalidation is scoped: adding a class to one element re-styles that element and its subtree, not the page.
  • Which is why a class toggle on <html> (a theme switch) is the expensive one.

~0:30. Selector cost is rarely the problem in practice; the number of elements that have to be re-styled is. Blink keeps invalidation sets per rule so a .read class on one paragraph doesn't touch its siblings. Two things that do break it: descendant selectors that depend on an ancestor's state (.dark .card p) and anything matching *. In the Performance panel this is "Recalculate Style", and the row tells you how many elements were affected.

Stage 4 · still no pixels

Paint produces a list of operations, not an image

// the display list for one card, roughly

  drawRRect(rect, radius: 8, #fff)
  clipRRect(rect)
  drawImageRect(hero.jpg, src, dst)
  drawTextBlob("Council votes on the bridge", …)

  • The main thread records what to draw, in order.
  • Recording is cheap; turning it into pixels (raster) happens elsewhere.
  • The same recording can be re-rastered at a new scale — pinch-zoom without re-running layout.
  • In the Performance panel: "Paint" is the recording, "Rasterize" is the pixels.

~0:34. Skia is the library doing this in Chromium; the display list is a Skia picture. The useful consequence: "paint" being expensive usually means the list is long or complicated (big blurs, many shadows, large repainted areas), not that the GPU is slow. A box-shadow with a 60px blur over a large area is the classic one, and the Rendering tab's paint flashing shows how much area is re-recorded.

Who covers whom, with no z-index at all

Paint order inside one stacking context

1  background and borders of the context's own element
2  negative z-index stacking contexts
3  in-flow, non-inline, non-positioned (blocks)
4  floats
5  inline content (text, inline boxes)
6  z-index: 0 / auto positioned elements
7  positive z-index stacking contexts
  • Later in the list paints on top. Within one step, DOM order decides.
  • So text paints over a float's background, and a positioned element paints over both — with no z-index anywhere.
  • This list repeats inside every stacking context, which is the next slide.

~0:36. Skip if late; the one line to keep, said on the next slide, is "positioned beats in-flow". Two everyday consequences: a position: relative with no z-index already wins over everything in-flow (step 6 beats step 3), which is why adding position: relative "fixes" an overlap; and two overlapping absolutely positioned siblings are decided purely by source order. Don't make them memorise the seven steps — make them remember that positioned beats in-flow and that order matters within a step.

A box that takes its children with it

What creates a stacking context

on purpose

  • position: relative|absolute + a z-index that is not auto
  • position: fixed or sticky (always)
  • isolation: isolate

by accident

  • opacity less than 1
  • transform, filter, backdrop-filter, mix-blend-mode, mask, clip-path
  • will-change naming any of those
  • contain: layout|paint, container-type, a flex/grid item with z-index

Inside a stacking context, z-index is local: the whole context is painted as one unit in its parent's order.

~0:38. If Paint order was skipped, say its one line here: positioned beats in-flow, and DOM order breaks ties. The phrase to leave them with: z-index only competes with its siblings. opacity: 0.99 is a real trick used to force one, and isolation: isolate is the honest way to say "my children's z-indexes stay inside". Where the pixels finally appear

Tiles, raster threads, and the image decode nobody measures

// a layer is rastered in tiles, off the main thread
layer (1600 × 4000)
  → tiles, viewport first
  → raster threads / GPU
  → textures the compositor can draw

// a 4000 × 3000 JPEG: decode costs ~50–150 ms
<img src="hero.jpg" decoding="async">

img.src = url;
await img.decode();   // decoded, not yet shown
slot.append(img);    // no flash of empty box
  • Only the tiles near the viewport are rastered; scrolling fast past un-rastered tiles is what "checkerboarding" is.
  • Image decoding is separate from downloading; a synchronous decode holds back the frame that needs the image.
  • decoding="async" lets the browser decode off-thread and paint the image a frame later.
  • Serve images at the size they are displayed: decode cost follows the source pixels, not the CSS box.

~0:44. Skip if late. The practical rule: a 4000px-wide hero shown in an 800px slot is five times the width and 25 times the pixels to decode and hold in memory, and no amount of CSS fixes that — srcset does. img.decode() is the one to reach for when swapping an image in a gallery or a carousel: set src, await decode(), then insert, and the swap never shows a blank. In the Performance panel the decode shows up as "Image Decode" on a raster thread.

The trap that undoes all of it

A non-passive wheel listener makes the compositor wait for you

  • With a blocking listener, a scroll gesture waits for a busy main thread before it starts, even though the compositor is free.
  • { passive: true } is a promise not to call preventDefault(). Breaking it logs an intervention warning and does nothing else.
  • At the console's Verbose level, Chrome logs "[Violation] Added non-passive event listener to a scroll-blocking 'wheel' event."
  • Try it in the demo: pick a listener in the dropdown, click Busy, then scroll the feed.

~0:48. Do the demo: click "Busy for 3 s" then immediately scroll the feed, with the listener set to none, then to { passive: true }, then to { passive: false } — only the last one janks. If a gesture genuinely needs preventDefault (a custom pinch-zoom, a canvas game), you can't be passive; then use touch-action / overscroll-behavior in CSS to tell the compositor up front what not to do.

What the user actually feels

Three numbers, three stages

LCP · loading
≤ 2.5 s

When the biggest element in the viewport appeared. Blocked by: slow TTFB, render-blocking CSS and JS, a late-discovered image.

INP · responsiveness
≤ 200 ms

From an input to the next frame that shows its result. Blocked by: long tasks on the main thread.

CLS · stability
≤ 0.1

How much visible content moved without the user asking. Caused by: layout after the first paint.

Measured on real users, at the 75th percentile. Your laptop on fast wifi is not the measurement.

~0:52. INP replaced FID in 2024 and is the strict one: it measures the whole interaction, including the frame that paints the result, and it reports close to the worst interaction on the page. The practical fix for INP is always the same shape: break the long task up (await scheduler.yield(), or do the work in a worker) and paint something before the expensive part. Lab tools (Lighthouse) approximate; field data (the Web Vitals library, CrUX) is the truth.

The article that jumps three times

Every shift is a layout that happened after a paint

causes

  • an image with no width / height: the box is 0 until it loads
  • a web font swapping in at a different size
  • a banner, cookie bar or ad injected above the content
  • a late fetch() that replaces a placeholder with taller content

fixes

A shift the user caused (clicking "show more") within 500 ms doesn't count. Everything else does.

~0:54. width and height attributes on an <img> are not legacy: the browser computes an aspect ratio from them and reserves the box before the bytes arrive. For the injected banner, the honest fix is to reserve the space or put it below the fold; "load it faster" doesn't fix a shift. Layout shift regions in the Rendering tab plus the Performance panel's Experience row give you the culprit element by name.

Cross-site scripting

If an attacker's script runs on your origin, the SOP protects it

  • It is your origin, so the browser allows all of it: same-origin reads, your cookies, your API.
  • The SOP limits reading responses, not sending requests: the exfiltration POST goes out.
  • A password field, a 2FA code, anything the page renders — all readable from the DOM as the user types.
  • Every defence after this slide exists because this code is so cheap to run.

~1:38. Say the sentence clearly: an XSS makes the attacker's code become your site. That is why "it's only a comment field" is never only a comment field, and why severity doesn't depend on what the demo payload does. alert(1) in a bug report is a proof of access, not the attack. Also kill the common defence-by-obscurity idea: minified code, obfuscated endpoints and "the token is in a weird key" change nothing here.

The shape of every DOM XSS

Untrusted data flows from a source into a sink

sources · data you don't control

  • location.href, .search, .hash, document.referrer
  • event.data from postMessage
  • API responses, including your own
  • localStorage, sessionStorage, cookies, IndexedDB
  • name of a window, a form field, a file name

sinks · places that parse or execute

  • innerHTML, outerHTML, insertAdjacentHTML, document.write, srcdoc
  • eval, new Function, setTimeout("…")
  • href, src, location set to a javascript: URL
  • el.setAttribute("onclick", …) or any other on* attribute
  • a <script src> whose URL comes from data

Auditing a page is this one question, repeated: does any source reach any sink?

~1:43. Give them the grep: search the project for the sink names, then trace backwards. Most real code bases have fewer than twenty hits, and each one is a yes/no question. Note the trap in the sources list: your own API is a source, because the comment in the database came from a user. "It's our data" is where stored XSS lives.

The first does not run. The second and third do.
<script> elements created by parsing a string are flagged "already started" and never run.

The "no <script>" rule is a spec detail about scripts inserted by parsing a string, and it fools a lot of people into thinking innerHTML is safe. Other payloads with no <script> in sight: <iframe srcdoc>, <a href="javascript:…"> that the page then clicks, <input autofocus onfocus>. Blocklists lose; the next slides are the things that win. Defence 1 · the one that always works

Untrusted text goes in as text

no

yes

  • textContent never parses: <img …> arrives as visible text.
  • <template> + cloneNode + textContent is the render pattern from Lecture 5, and it was already safe.
  • URLs still need a check: textContent can't help an href="javascript:…".

~1:48. Escaping, if it comes up, is context-dependent: HTML text, an attribute value, a URL and a JavaScript string all need different rules — which is why "insert as text" beats "escape correctly". Say plainly that this covers the overwhelming majority of real cases: almost nobody needs user-supplied HTML. When a framework is in play the same rule has a different name — React's dangerouslySetInnerHTML, Vue's v-html, Angular's bypassSecurityTrustHtml — and each one is a grep worth doing. The exception is a rich-text editor's output, which is the next slide.

Defence 2 · when you genuinely need HTML

Let a sanitiser decide which tags survive

  • An allowlist of elements and attributes, applied after parsing — never a regex over the string.
  • Sanitise as late as possible, on output. Storing sanitised HTML means a bug in the sanitiser is now permanent.
  • setHTML() is new and engine support still differs: keep a library fallback.

~1:51. Check caniuse the morning of the class for setHTML() and Trusted Types, and say the date and versions out loud. The Sanitizer API's shape changed more than once during standardisation, so verify on MDN before demoing. DOMPurify is the battle-tested option and is the one to use in the exercise. One concrete example of context-dependent escaping: <a title=" + user text is fine escaped for HTML, but the same text in href can still be javascript:.

Defence 3 · make the unsafe thing impossible

Sinks stop accepting strings at all

// a CSP response header (next slide)
Content-Security-Policy:
  require-trusted-types-for 'script';
  trusted-types recipes-policy dompurify;
  • With the policy on, assigning a plain string to innerHTML throws: "did we sanitise everywhere?" becomes a type error.
  • Every unsafe assignment has to go through a named policy — one place to review, one place to fix.
  • You find them all at once: turn it on in report-only mode and read the violation reports.
  • The code it forces you to write is safe in every browser, whether or not that browser enforces it.

~1:53. This is how large sites eliminate DOM XSS as a class rather than fixing instances: Google has published that Trusted Types plus a strict CSP removed almost all of their DOM XSS reports. Partial support is fine — it is a development-time guarantee. Guard the policy with if (window.trustedTypes) (or a tinyfill) so the same code runs where the API is missing. The header names dompurify too: DOMPurify creates its own policy, and without it sanitize() silently returns an empty string under enforcement. Keep the number of policies small; a policy named "default" applies everywhere and is a tempting escape hatch.

Content Security Policy

A header that says where code may come from

// a strict, nonce-based policy
Content-Security-Policy:
  script-src 'nonce-r4nd0m' 'strict-dynamic';
  object-src 'none';
  base-uri 'none';
  require-trusted-types-for 'script';
// and in the page, per response
<script nonce="r4nd0m" src="/app.js"></script>
<script>trackPageView()</script>   ← blocked: no nonce
  • A <script> injected into server-rendered HTML (stored or reflected) has no nonce, so the browser refuses to run it.
  • Inline event handlers are blocked by any script-src without 'unsafe-inline': onerror= stops working.
  • The nonce is new on every response. A nonce in a cached static file protects nothing.
  • 'strict-dynamic' lets a trusted script load more scripts, so bundlers and loaders still work.

~1:56. Why nonces beat host allowlists: script-src https://cdn.example trusts every file on that CDN, including some old AngularJS copy that will happily evaluate a template from the DOM. Google's research on real policies found host allowlists bypassable on the large majority of sites, which is why the recommended shape is nonce + 'strict-dynamic'. Its limit: a trusted script can still create <script src> from data — the last sink on the sources-and-sinks slide. CSP is a second line: it does not fix the injection, it limits what the injection can do.

In the CTF you will read a token out of localStorage through an XSS, and fail to read the HttpOnly cookie beside it.

~2:01. The honest nuance: HttpOnly doesn't stop an XSS from using the session — the attacker's fetch still carries the cookie. It stops exfiltration, which turns a permanent account takeover into an attack that only works while the page is open. That is a real difference, and it is why a token in localStorage is strictly worse than a cookie you can't read. On SameSite: only Chromium defaults to Lax, and even there a fresh cookie is sent on cross-site POSTs for two minutes ("Lax+POST"). Firefox and Safari have no such default. Always set the attribute.

  • The attacker can't read the response (SOP) — the write already happened.
  • A cookie set with SameSite=Lax isn't sent on a cross-site POST, so the form arrives logged out.
  • Belt and braces on the server: check Sec-Fetch-Site / Origin, or a per-session CSRF token.
  • Any state-changing request should be a POST/PUT/DELETE, never a GET a link can trigger.

~2:04. Why it still matters with Lax set: top-level GET navigations do send the cookie, so a GET that changes state ("/unsubscribe?id=…") is still exploitable with a plain link; and an API that accepts JSON with SameSite=None cookies for a legitimate cross-site setup is back to square one. The modern minimum: SameSite=Lax plus an Origin check on the server.

Your page, invisible, under their button

The user clicks "Play". The click lands on "Delete account"

// the fix, as a response header
Content-Security-Policy: frame-ancestors 'none';
// or, to allow your own pages only
Content-Security-Policy: frame-ancestors 'self';

// the older header, still understood
X-Frame-Options: DENY
  • Nothing is read and nothing is injected: the attacker borrows the user's clicks.
  • frame-ancestors says who may frame you — a directive <meta> cannot set.
  • Default to 'none' for anything with a destructive action or a session.

~2:09. Historical note worth 20 seconds: this is why important dialogs moved into the browser UI (permission prompts, the file picker) — page-drawn confirmations can be framed and covered, browser-drawn ones cannot. Also mention that sticky overlays and "are you sure?" modals are not protection, and that SameSite=Lax or Strict is a strong mitigation: a cross-site frame doesn't get the session cookie, so the framed page loads logged out. The attack needs a SameSite=None session or a same-site attacker. The CTF works because localhost on another port is the same site — say so at the debrief.

The other direction

Embedding someone else's page: say what it may do

<iframe src="https://widgets.example/print"
  sandbox="allow-scripts allow-same-origin allow-modals"
  allow="fullscreen"
  referrerpolicy="no-referrer"
  loading="lazy"></iframe>
  • sandbox with no value removes everything: no scripts, no forms, no popups, and a unique opaque origin.
  • Add back only what the widget needs: allow-scripts, allow-forms, allow-modals (for print()), allow-same-origin (its real origin, so messages carry it).
  • allow-scripts allow-same-origin on a frame of your own origin gives it full access again — that pair is the trap.
  • allow is Permissions Policy (Lecture 11): a cross-origin frame gets fullscreen, camera, geolocation only if listed.

~2:11. The pattern to remember: a sandboxed iframe is the only real way to run untrusted HTML or a third-party script with a boundary around it — same-origin isolation inside your page does not exist, since a script on your origin can reach everything. If a product requires "embed this snippet", an iframe keeps it out of your DOM; a <script> tag does not (Lecture 10).

Talking across the boundary on purpose

Two checks, every time

  • Any window that has a reference to yours can post to you: a frame, an opener, a popup.
  • Without the origin check, the message channel is an open API on your origin.
  • "*" as the target means whatever origin the frame has navigated to can read the message.
  • event.data is a source: it must never reach a sink unchecked.

~2:13. This is flag 4 in the CTF, in the other direction: there the vulnerable receiver is the widget, listening to its parent. Its check compares e.origin to the embedder's origin and e.source to parent. The widget acts on any message, so a page the attacker controls frames it and sends one. Two refinements if asked: MessageChannel gives you a private port pair so you don't have to filter at all, and e.origin on a sandboxed frame's message is "null" — comparing it to a string you expect will correctly fail.

If asked about target="_blank": it implies noopener in every current browser, so the opened page can't navigate yours (tab-napping); window.open doesn't, and needs the flag. Cross-Origin-Opener-Policy: same-origin cuts the link for every window, and together with COEP it lets a page use SharedArrayBuffer and precise timers, which browsers disabled after Spectre.

Act 3 on one slide

The checklist for a page you ship

  1. No untrusted data in an HTML sink. textContent and <template>; sanitise only when HTML is the feature.
  2. A CSP, nonce-based, report-only first. require-trusted-types-for 'script' if you can.
  3. Session in a cookie: HttpOnly, Secure, SameSite, __Host-. No tokens in localStorage.
  4. State changes are POST, with an Origin / Sec-Fetch-Site check on the server.
  5. frame-ancestors on anything with a destructive action.
  6. Frames in: sandbox + allow. Messages in: check origin and shape.
  7. Dependencies: pinned versions, integrity, as few as possible (Lecture 10).

~2:16. Read it as the CTF brief: each flag in the next exercise is one of these lines missing. Tell them the order matters — lines 1, 4 and 5 prevent; lines 2 and 3 limit the damage when line 1 fails. A site with a perfect CSP and an unsanitised comment field is still breached; a site with line 1 right and nothing else is in decent shape.

Today, in one slide

Inside the browser

processes

Browser process, renderers never shared between sites, GPU, utilities. A renderer is sandboxed and asks over IPC.

threads

Main thread: parse, style, layout, paint, your JavaScript. Compositor: scrolling and transform / opacity.

loading

HTML streams and parses incrementally. Classic scripts block it, defer doesn't, CSS blocks the first paint. LCP, INP and CLS measure what the user feels.

rendering

The layout tree is not the DOM. Stacking contexts make z-index local. Layers move without repainting.

origins

Same-origin policy is the boundary. An XSS runs as you, so the SOP doesn't help.

defences

Don't parse untrusted data. CSP, Trusted Types, cookie attributes, frame-ancestors, origin checks.

For any page, yours or someone else's

Three questions that fit on a sticky note

  1. Which stage is the user waiting on — parse, style, layout, paint or composite?
  2. Which thread runs it, and what else is queued on that thread?
  3. Whose code runs on this origin, and what can it read?
