HTTP/1.1 · a request

A request is text: a line, headers, a body

POST /api/stalls/taco-bike/reviews HTTP/1.1
Host: localhost:3000
Content-Type: application/json
Accept: application/json
Content-Length: 66
⏎ an empty line ends the headers
{"author":"Ana","rating":5,
 "text":"Best tacos on the waterfront."}
  1. Method: what to do. GET reads, POST creates.
  2. Target: the path (and query) of the resource.
  3. Headers: metadata, Name: value. Names are case-insensitive.
  4. Body: optional. Its format is declared by Content-Type.

~0:06. HTTP/2 and HTTP/3 send the same information in binary frames over one connection, but the model (method, target, headers, body) is identical, and DevTools shows it in this form. Over HTTPS all of it is encrypted, including the path and headers; only the host name is visible to the network.

HTTP/1.1 · a response

A response: a status, headers, a body

HTTP/1.1 201 Created
Content-Type: application/json; charset=utf-8
Location: /api/reviews/r17
Cache-Control: no-store

{
  "id": "r17",
  "stallId": "taco-bike",
  "author": "Ana",
  "rating": 5,
  "text": "Best tacos on the waterfront.",
  "createdAt": "2026-10-16T19:42:07.311Z"
}
  1. Status: a three-digit code and a reason phrase. The code is the contract; the phrase is for humans.
  2. Headers: Content-Type says how to read the body; Location says where the new resource lives.
  3. Body: here, the review as the server stored it, with fields the client didn't send.

Point at id and createdAt: the server chose them. That's why, in Act 4, the page renders the response body rather than the object it sent.

URL

A URL, and the part called the origin

https://schememarket.examplehost:443port/api/stallspath?tag=food&sort=pricequery#vendorsfragment

origin = scheme + host + port → https://market.example

Query: key-value pairs for the server (filters, sorting, pages). Build it with URLSearchParams: it encodes &, spaces and # for you.

Fragment: never sent to the server. Origin: the unit of browser security, back in Act 5.

The string-concatenation version, `/api/stalls?q=${value}`, breaks on "rock & roll": the server sees q=rock and a parameter called roll. The port is implicit when it's the scheme's default (443 for https, 80 for http), which is why the origin above has no :443.

~0:09. The two properties are what clients and proxies rely on: a browser may retry a GET; nobody should silently retry a POST, because that's how you get two reviews (Act 4). JSON · revisited

The body is text. JSON has six types.

Strings, numbers, booleans, null, arrays, objects. Nothing else crosses the wire.

Dates travel as ISO 8601 strings in UTC. Convert on the client, display in the user's time zone.

A typed language on the server doesn't make your data typed: validate what arrives, on both sides.

~0:12. Lecture 5's Set trap again, now with a network in between. Money is usually sent as integer cents or a decimal string: 0.1 + 0.2 in JavaScript is the reason. Large integer ids (above 253) lose precision in JSON numbers: APIs send them as strings.

Why asynchronous

JavaScript runs on one thread, shared with the page

One call stack. Your scripts, your event handlers and the page's rendering take turns on the main thread.

The browser waits, not your code. Network, timers and file reads run outside JavaScript; when they finish, a callback is queued.

A promise is the handle to a result that doesn't exist yet: pending, then fulfilled with a value or rejected with an error.

~0:24. Run the while loop in the console of any page and try to scroll: that's what a blocking network call would do to every page on every request. Synchronous XMLHttpRequest exists and is deprecated for exactly this reason. "Asynchronous" here means: start the operation, give the browser something to call later, keep going.

Quick check · predict the output

Five lines. In which order do the letters print?

A E D B C
Synchronous code first (A, E). Then microtasks, the promise callbacks (D). Then one task, the timer (B). The network answers last (C).
A 0 ms timer means "as soon as possible after the current code", never "now". Step through it on the next slide.

~0:25. Get three or four predictions before revealing; most people say A B C D E or A E B D C. The point to keep: a callback never interrupts running code. It waits until the stack is empty, and promise callbacks go ahead of timers and events.

~0:31. "Task" is the spec's word; older articles say "macrotask". There are several task queues (timers, user input, networking) and the browser picks which to serve next, usually favouring input; within one source, tasks keep their order. There is one microtask queue. fetch touches both: the response arriving is a task, which settles the promise; your .then callback is then a microtask. Consequences: a long task delays rendering and every click behind it; a microtask that queues another microtask forever freezes the page just like a while (true), because the loop never gets back to rendering; a setTimeout loop doesn't, because each round is a new task. Timers nested five deep are clamped to at least 4 ms, and background tabs throttle them to once a second or less. The third bucket is the classic trap: a Promise executor and a programmatic el.click() run synchronously; only a real user click is a task. Node has the same two levels (plus process.nextTick, which runs before promise callbacks), with its own task phases instead of rendering.

Quick check · which queue?

Seven letters. In which order?

C A G D F E B
No queue: the executor (C) and button.click() (A) run synchronously, then G. Microtasks in order: D, F, then E, which D queued: the loop drains the queue, newcomers included. Then one task: B.
A real click is a task: its A would print after all of this, never in the middle of the script.

E is the one that tests the rule: it's queued while the microtask queue is being drained, and it still runs before B. requestAnimationFrame is left out on purpose: whether it runs before or after a 0 ms timer depends on where the frame boundary falls.

Promises · the chain

.then, .catch, .finally

.then(f) returns a new promise: f's return value fulfils it, a returned promise is waited for, a throw rejects it.

.catch(f) handles a rejection from any step before it. .finally(f) runs after either outcome.

No .catch anywhere: Uncaught (in promise) in the console.

~0:31. The two mistakes: forgetting return inside a .then (the next step gets undefined and doesn't wait), and nesting .then inside .then instead of returning (the "pyramid" that promises were meant to remove). Before promises, async APIs took callbacks: setTimeout(callback, ms) is one; error handling with callbacks is why promises exist.

async / await

The same code, two styles

.then / .catch

async / await

async/await is syntax over promises: an async function returns one, await waits for one and throws if it rejects. Independent requests: start both, then await Promise.all([a(), b()]).

~0:33. Today's code uses await; libraries, docs and older code use .then, so they need to read both. await works inside async functions and at the top level of modules (the project's main.js). The exercise editors run classic scripts, so there it's .then() or an async function start(). A common slowdown: await a(); await b(); runs them one after the other even when they're independent.

fetch()

Two awaits: first the head, then the body

The first promise resolves as soon as the status and headers arrive. The body may still be downloading: json() reads the rest of the stream and parses it, so it's a second promise.

~0:34. The two-step design lets you decide what to do from the status before downloading a large body, or abort it. Other body readers: text(), blob(), formData(); the body can be read once. fetch(url) with no options is a GET. Relative URLs resolve against the page: /api/stalls on a page served from localhost:3000 means http://localhost:3000/api/stalls.

Quick check · fetch and errors

The stall doesn't exist. What happens?

render is called with { error: "not_found", message: … }. No exception: a 404 is a response, and fetch resolves.
fetch rejects only when there is no usable response: network down, DNS failure, CORS blocked, aborted. Then it's a TypeError (or an AbortError).
So every caller checks response.ok. Write it once, in a helper.

~0:36. The most common fetch bug in production code. axios and most other HTTP libraries reject on 4xx/5xx; fetch deliberately doesn't, because a 404 can be a perfectly good answer ("no such user: show the sign-up form").

The lifecycle of a request

Every list from a server has four states

loading

Request in flight. Say so; keep the old data visible if there is some.

ready

The data. What we've rendered since Lecture 5.

error

No data. A sentence, and a way out: Try again.

empty

Success with []. Not an error: "No stalls yet".

Designs usually show only ready. The other three are where apps feel broken: a blank list on a slow connection, a spinner that spins forever after an error.

~0:55. Today's code (slide 28, the project) blanks the list while loading, the simple version; keeping the old results dimmed is in team brief 3. State

After a 201

Render what the server stored, not what you sent

Pessimistic (today)

Wait for the 201, then render the response body: it has the id, the createdAt, the trimmed text. The page shows the truth.

Optimistic

Render immediately, send in the background, roll back if it fails. Feels instant; needs a temporary id and an undo path.

~1:35. Optimistic UI suits actions that almost never fail and are cheap to undo: a ♥, a like. It's one of the team-build briefs ("Saved on the server"). For a review that the server may reject for validation reasons, pessimistic UI avoids showing something that then disappears.

The browser validates for speed. The server validates because it must.

~1:36. required and maxlength catch the obvious before a request is sent; anyone can send a request without your form (curl, DevTools), so the server is the only place a rule is enforced. Two ways to read a 422: branch on response.status with plain fetch (Exercise 4), or catch the HttpError that api.js throws and read error.body.fields (the team build). showErrors(fields) puts each message in the .field-error with the matching data-for and sets aria-invalid; it's Exercise 4's case 2. Never clear the form after a failure. The 10-character minimum exists only on the server, so the client can't know about it. A real form links each message with aria-describedby and moves focus to the first invalid field.

Double submits

Click twice, get two reviews: POST is not idempotent

Client: disable the control while pending; re-enable in finally.

Server: an Idempotency-Key header (a UUID per submission); repeats are ignored. Payment APIs support it.

Design: make it idempotent where you can: PUT /api/saved/mezcal, not POST /api/saved.

~1:38. Double submits come from slow networks, impatient users, and automatic retries. A disabled button is enough for this course; the Idempotency-Key is what makes "retry on timeout" safe for a POST. crypto.randomUUID() generates the key.

The other methods

PUT, PATCH, DELETE, and a header for auth

No token or an invalid one: 401. A valid token that may not edit this stall: 403. A real token never goes in your source: it comes from a login.

~1:40. With the project's helper these are request("PUT", "/saved/mezcal") and so on. DELETE returning 404 when the thing is already gone is a design choice; some APIs return 204 to stay idempotent in the response too.

The same-origin policy

A page may send simple requests anywhere. Reading the response is the question.

Page at http://localhost:3000 fetches…Same origin?Why
http://localhost:3000/api/stallsyesscheme, host and port match
http://localhost:8080/api/stallsnodifferent port
https://localhost:3000/api/stallsnodifferent scheme
http://127.0.0.1:3000/api/stallsnodifferent host, even if it's the same machine
https://api.open-meteo.com/v1/forecastnoallowed anyway: that server sends CORS headers

Why: your browser holds cookies for your bank. Without this rule, any page you visit could read bank.example/account with your session.

~1:54. Non-simple requests (a JSON POST, an Authorization header) aren't even sent without the server's permission: next slide. The point of the policy is the user's credentials and private network, not the server's data: curl can read any public API, because curl has no cookies of yours. CORS (next slide) is how a server opts in to being read by pages from other origins.

CORS · Cross-Origin Resource Sharing

The server says who may read its responses

Browserpage at localhost:8080
Serverlocalhost:3000
preflight: "may I?"
OPTIONS /api/stalls/taco-bike/reviews · Origin: http://localhost:8080 · Access-Control-Request-Method: POST · …-Headers: content-type
204 · Access-Control-Allow-Origin: http://localhost:8080 · Allow-Methods: GET, POST, PUT, PATCH, DELETE · Allow-Headers: Content-Type, Authorization
"yes"
the real request
POST /api/stalls/taco-bike/reviews · Origin: http://localhost:8080
201 · Access-Control-Allow-Origin: http://localhost:8080 · {…}
readable

Simple (GET, HEAD, or a POST with a form or text body, no custom headers): no preflight, it reaches the server. A JSON body, PUT / PATCH / DELETE or Authorization: preflight first.

~1:56. Without Access-Control-Allow-Origin on the response, the request may still have reached the server and done its work (for a simple request); the browser just refuses to hand the response to JavaScript. The preflight exists so that non-simple requests (which older servers never expected from a browser) are not sent at all unless the server agrees. Access-Control-Allow-Origin: * is fine for public data; it's not allowed together with credentials (cookies).

AbortController · AbortSignal

Cancel the request you no longer need

The aborted fetch rejects with an AbortError; its render never runs. The browser cancels the request: no more bytes are downloaded.

AbortSignal.timeout(ms): a timeout. AbortSignal.any([a, b]): whichever comes first.

Also for: leaving a page or closing a dialog while its data is loading.

~2:03. On HTTP/1.1 cancelling closes the connection; on HTTP/2 it resets only that stream. Aborting doesn't undo anything on the server: an aborted POST may well have been stored. Abort reads freely; for writes, abort only means "I stopped waiting".
