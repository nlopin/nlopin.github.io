HTML and SVG are markup: the browser keeps the elements and redraws them for you when something changes (retained mode). Canvas has no markup at all, only a drawing API: you issue commands, the browser keeps the pixels and forgets the shapes (immediate mode). If anything changes, you clear and draw everything again. The SVG numbers are the canvas numbers: both use their own coordinates, y growing downwards. The HTML version needs one CSS rule, not shown: .chart { display: flex; align-items: end; gap: 5%; }, and the bars a width. Neither surface is better; they cost different things, which is the rest of this act.

Surface 1 · boxes

You already draw with HTML

  • A bar is a div with a height. A row of bits is a grid of 8 cells.
  • Text, wrapping and fonts for free. With the right elements (buttons, tables), focus and screen readers too.
  • Layout does the positioning; you set sizes in % or with custom properties.
  • Good when the picture is boxes that line up: bars, grids, tables.

~0:06. A common mistake is reaching for canvas for something that is really a table or a grid. If the picture is made of rectangles that line up, HTML and CSS draw it, and Lecture 3's layout does the hard part. Setting --share from JavaScript (el.style.setProperty("--share", 0.4)) keeps the maths in CSS.

Two ways to store a picture

Vector: a list of shapes. Bitmap: a grid of pixels.

SVG · a circle in a 24 × 24 viewBox · shown at 240 px

  • Stores shapes: "a circle at (12, 12), radius 9".
  • Turned into pixels when drawn, at the screen's resolution: sharp at any size.
  • Size grows with the number of shapes. SVG, font outlines.

PNG · the same circle, 24 × 24 pixels · shown at 240 px

  • Stores pixels: one colour per cell; in memory, 4 bytes each (RGBA).
  • Fixed resolution: enlarged, it turns blocky or blurry.
  • Size grows with width × height. PNG, JPEG, a canvas.

~0:06. Both pictures here really are what the captions say: the left one is an inline SVG circle, the right one is a real 24 × 24 PNG (images/circle-24.png) shown with image-rendering: pixelated, so each of its 576 pixels is a visible square; with default smoothing it would look blurry instead. On screen everything ends up as pixels: the difference is when they are made. A vector is rasterised by the browser at draw time, for whatever size and screen density it's shown at; a bitmap already is pixels and can only be resampled. That's why an SVG stays sharp on a 2× screen and a canvas needs the devicePixelRatio fix (slide "The blurry canvas"). Memory: a 400 × 200 bitmap is 400 × 200 × 4 = 320 000 bytes uncompressed, whatever is drawn on it; PNG and JPEG compress it for storage. The two mix: SVG can contain bitmaps (<image>), and a canvas can draw paths, which become pixels the moment they're drawn.

Surface 2 · SVG

SVG: a markup language for vector graphics

  • Scalable Vector Graphics: XML-based markup that describes shapes. The browser draws them sharp at any size.
  • Inline in HTML, every tag becomes a DOM element: in the Elements panel, selectable by CSS, with its own events.
  • As a file (<img src="chart.svg">) it's an image: your page can't reach the elements inside.
  • viewBox="0 0 400 200": your units, scaled to any size on screen. y grows downwards from (0, 0) at the top left.

~0:07. Precise wording matters here: SVG is a language, not "the DOM". A standalone .svg file is XML and must be well-formed; SVG written inside an HTML file is parsed by the HTML parser into SVG elements (SVGRectElement, …) in the same DOM tree as the page. Only that inline form gives you elements to style, script and click; through <img> or a CSS background it's a picture. The viewBox is the key idea: draw in convenient numbers (400 × 200), let CSS decide the size on screen (width: 100%). Strokes scale with it, unless vector-effect: non-scaling-stroke. Shapes are painted with fill and stroke, not background and border; both are attributes and CSS properties. Because inline shapes are elements, Lecture 5's render(state) works unchanged, and Friday's transitions animate them.

Live · a path from an array

A line chart is one path

~0:08. M x y moves the pen, L x y draws a line to a point, Z closes the shape; C draws a Bézier curve. Live: add + " L 400 200 L 0 200 Z" and change fill: an area chart. The two arrow functions x and y are what chart libraries call scales: domain (your numbers) to range (pixels). That's a linear scale; libraries add log, time and band scales, ticks and round numbers on top.

~0:09. The triangle: move to (10, 90), line to (50, 10), line to (90, 90), close. The curve starts at (120, 90) and ends at (210, 90); the dots are its two control points: the curve leaves towards the first and arrives from the direction of the second, without touching either. Commas and spaces are interchangeable. Two more letters exist: S and T, smooth versions of C and Q that reuse the previous control point. A command letter can be omitted when it repeats: after an M, extra coordinate pairs are treated as L. For the arc's five flags and numbers, see MDN; the arc is the one nobody writes by hand twice.

Surface 3 · canvas

A canvas holds a bitmap: draw everything, every time

~0:10. After fillRect the canvas doesn't know there was a rectangle: there is nothing in the Elements panel, nothing to click, nothing for CSS. That's why it's fast for thousands of things, and why render() clears and redraws all of it. In an animation, that render runs in Friday's requestAnimationFrame loop. Change 5000 to 50 000: still instant. The same in SVG would be 50 000 elements.

Trap · on high-density screens

The blurry canvas

A canvas has two sizes. CSS size: how big it looks. width / height attributes: how many pixels it stores.

On a 2× screen, a 400 px wide canvas shown 400 CSS px wide is stretched over 800 real pixels. Text and thin lines go soft.

~0:11. Run it again on resize (a ResizeObserver on the canvas). Setting canvas.width also clears the canvas and resets the context, including the scale: that's why the ctx.scale comes after it. SVG and HTML don't have this problem: they're vectors and text, redrawn at the screen's resolution.

Clicks · SVG vs canvas

Which dot did I click?

SVG: the browser finds the shape

canvas: you find it, with maths

SVG: each shape is an element, so event.target is the circle you clicked. Canvas: the event's target is the whole canvas; which dot is under the pointer is your code.

~0:12. The SVG version is Lecture 4's delegation: one listener on the svg, closest to find the shape. The browser hit-tests the painted outline: by default a shape with fill="none" only reacts on its stroke (pointer-events changes that). Hover comes free too: circle:hover in CSS. In canvas there is no hover either: you'd listen to pointermove and run the same maths. The scale factor matters when the canvas is shown at a different size than its width / height; after the devicePixelRatio fix with ctx.scale, you draw in CSS pixels and the factor drops out (you'd compare in CSS pixels instead). find is a loop over every dot on every click: fine for thousands, a spatial index for millions.

~0:33. What each one cost after the download, read from Chrome traces (stages are medians of 5 runs; they vary a little run to run). The script: parsed and compiled by V8 in the background while it downloads (v8.parseOnBackground); then run on the main thread (EvaluateScript), where functions are compiled lazily the first time they're called; hot functions get optimised later by V8's Maglev compiler on a worker. The image: decoded on a worker (ImageDecodeTask), nothing image-specific on the main thread. DevTools' CPU throttling slows only the main thread, which is why the worker bars don't grow at 4×. And D3 is a gentle case: loading it mostly defines functions. An app that renders, fetches and wires up listeners at start-up runs far more on the main thread; the next slide shows a real one. Tom Dale's line, quoted on web.dev ("JavaScript Start-up Optimization"): "Byte-for-byte, JavaScript is more expensive for the browser to process than the equivalently sized image or Web Font." Same bytes means same bytes on the wire: JavaScript compresses well (280 kB → 92 kB here), a JPEG is already compressed.

Lecture 8, again

Your JavaScript and the page's drawing share one thread

  • The main thread runs your handlers, recalculates styles, lays out and records paint. One thing at a time.
  • A screen at 60 Hz wants a new frame every 16.7 ms; at 120 Hz, every 8.3 ms.
  • While your handler runs, no other handler, no style or layout update runs: keystrokes and clicks wait. (Scrolling and transform / opacity animations can go on: another thread, the compositor, runs them.)

Before you record

Your laptop is not representative

  • The Performance panel's settings: CPU throttling 4× or 6×.
  • Developer machines are fast. Your users' phones and older laptops are not: the Reddit chart, 0.35 s vs 2.6 s.
  • Record with throttling on: at 4×, a 30 ms problem becomes a 120 ms one you can see.
  • Network throttling (Fast 4G, Slow 4G) is the same idea for downloads: Act 4.
rule of thumb

Under 100 ms feels instant. Chrome's Interaction to Next Paint (INP) metric rates over 200 ms "needs improvement", over 500 ms "poor".

~0:37. Throttling slows the CPU for this tab, not the network, and only its main thread: worker threads run at full speed (measured on the JS-vs-image slide). It's an approximation: mobile CPUs also have less memory and worse thermals. INP is one of the Core Web Vitals; the Performance panel's start screen shows it live for whatever you click on the page.

Reading the recording

x is time, y is the call stack, width is cost

  1. Find the long task. Grey bar with a red corner at the top of the Main track.
  2. Look below it. Each row is one level deeper in the call stack: render calls row 87 554 times. The profiler samples, so row shows as slivers or merged bars, not 87 554 bars.
  3. Ask "which colour?" Yellow: your JS. Purple: the browser laying out what you built.
  4. Bottom-Up tab: functions sorted by self time, the time spent in the function itself, not its callees.
self vs total

Total time includes everything a function calls; self time is its own lines only. Big total, small self: the cost is further down. Follow it until the self time is big.

Fewer things · the price

What virtualisation costs

  • Row heights must be known. Fixed heights are easy; variable heights need measuring and estimates.
  • Ctrl F finds nothing that isn't rendered. Neither do in-page links.
  • Screen readers see only the rendered rows: aria-setsize and aria-posinset (in a table: aria-rowcount, aria-rowindex) say where they are.
  • Focus is lost when the focused row scrolls out and is removed.
when not to

A list of a few hundred rows doesn't need it. Measure first: if the recording shows no long task, the simple version wins.

~1:24. The trade-off slide. Many apps choose pagination or "load more" instead precisely because of these costs: it keeps find-in-page, links and accessibility working.

Content delivery network

A CDN keeps copies of files on servers near the users

browserasks for a URL
nearby
edge serverone of many, in many cities
(points of presence)
only on a miss
originthe server with the original file
  • Cache hit: the edge has a copy and answers itself.
  • Cache miss: the edge fetches from the origin, answers, and keeps a copy.
  • DNS points the hostname at the CDN, and the request reaches a nearby edge.
  • The origin decides how long copies may be kept: the Cache-Control header.

~1:56. Why it matters: latency is mostly distance, and every request pays at least one round trip; a nearby edge makes that trip short. The origin also gets only the misses, not every request. Large CDNs: Cloudflare, Fastly, Akamai, Amazon CloudFront. How a request finds a nearby edge depends on the CDN: some answer DNS with a nearby server's address, Cloudflare announces the same addresses from every location (anycast) and the network routes to the closest. It's not only for libraries: this course's pages on GitHub Pages are served through Fastly, and the Lecture 8 API (harbour-api.lopin.me) runs on Cloudflare's network.

DevTools → Network → a request → Headers

You can see the CDN in the response headers

lopin.me · GitHub Pages

via: 1.1 varnish

cdn.jsdelivr.net · d3@7.9.0

               s-maxage=31536000, immutable

cf-cache-status: HIT
  • Standard HTTP: Cache-Control (who may keep a copy, and for how long: max-age in seconds), Age (seconds this copy has been in the cache: here 86 days).
  • Vendor headers: x-cache, x-served-by (Fastly), cf-cache-status (Cloudflare): hit or miss, and which edge answered.

~1:58. Both captured with curl -I while writing this deck; run it again and the values change. The left one: GitHub Pages behind Fastly (Varnish is Fastly's cache software); TOJ is the code of the Fastly location that answered (Madrid), and it didn't have a copy yet. The right one: jsDelivr's file came from Cloudflare's edge, which had held it for 86 days. max-age=31536000 is one year; s-maxage is the same limit for shared caches like a CDN; immutable tells the browser not to even revalidate. A CDN can promise that only for URLs whose content never changes: that's why the version is in the URL.

CDNs for open-source packages

Package CDNs serve the npm registry as URLs

https://schemecdn.jsdelivr.nethost/npm/registryd3package@7.9.0version/+esmfile · build
  • npm is the registry where JavaScript packages are published. Millions of them.
  • jsDelivr, unpkg, esm.sh fetch packages from the npm registry (their origin) and serve any file in them through a CDN. (cdnjs hosts a curated list instead.)
  • Remove the file part and jsDelivr lists every file in the package: cdn.jsdelivr.net/npm/d3@7.9.0/

~2:00. jsDelivr's /+esm and esm.sh convert a package to an ES module on the fly, rewriting its own imports into more CDN URLs. d3@7.9.0/+esm is a 1.5 kB file that imports 30 more: look at it in the Network panel.

Way 1 · the oldest

<script src>: the library becomes a global

  • The file is a UMD build: it puts one global on window (L, Chart, d3).
  • Order matters: the library's tag before yours.
  • Globals share one namespace with your scripts: a library's d3 and your own d3 variable, and one silently hides or overwrites the other.
  • Some libraries need their CSS too.

~2:01. Still the most common snippet in READMEs, and still fine for a single library. defer on both tags keeps the order and doesn't block parsing.

Way 2 · ES modules

Import from a URL, in a module

  • No globals: the names exist in this module only (Lecture 5).
  • Named { formatHex }, default confetti, namespace * as d3: which one works depends on what the package exports. The README says.
  • Only inside type="module".
Uncaught SyntaxError: Cannot use import statement outside a module

~2:03. The error appears when the script tag lacks type="module". If a default import gives undefined or "does not provide an export named default", try the namespace import and log it: console.log(d3) shows what's inside. The @4 on culori is on purpose: two slides later we see why it should be exact.

Way 3 · what the docs show

Bare names fail in the browser

Uncaught TypeError: Failed to resolve module specifier "d3". Relative references must start with either "/", "./", or "../".

"d3" is a bare specifier: a package name, not a URL. Node and bundlers know where npm packages live (node_modules). The browser only knows URLs.

~2:04. Nearly every README and nearly every AI answer writes imports this way, because nearly every project has a build step. Firefox's message: "The specifier “d3” was a bare specifier, but was not remapped to anything." Two ways out: replace the name with the URL in every file, or tell the browser once: the import map.

One place for every dependency

An import map: names to URLs

  • Every module on the page can now import … from "d3", as the docs write it.
  • Every version in one file. Upgrading is one line.
  • It must come before the module scripts that use it.
  • A URL or a local path: the code doesn't care which.

~2:06. Supported everywhere since 2023. The second entry previews vendoring (slide "Vendor it"): switching from CDN to a local copy changes the map, not the code. A trailing-slash entry ("lodash/": "https://…/lodash-es@4.17.21/") maps a whole folder, for packages imported by path.

Semantic versioning

Pin the version, or the code changes under you

7major · breaks things.9minor · adds things.0patch · fixes things
…/npm/d3/+esmlatest. Can become a new major at any moment.
…/npm/d3@7/+esmthe newest 7.x. Safer, still moves.

~2:10. Semver is a promise, not a guarantee: minors occasionally break things too. A pinned +esm URL keeps the version, not the bytes: jsDelivr generates those files and may rebuild them. Static files (dist/d3.min.js) never change, and only those work with the next slide's integrity hashes; jsDelivr itself says not to use them on generated files.

Trap · the code is from another era

The AI's code was right, for D3 v3

Uncaught TypeError: Cannot read properties of undefined (reading 'linear')
  • d3.scale.linear() is D3 v3. Since v4 (2016) it's d3.scaleLinear(). Models learned from years of old examples.
  • Compare the version the code assumes with the version you load. Ask for the version explicitly.
  • Big jumps have a migration guide or a CHANGELOG.md. Read the one for your major.

~2:11. Same family: Chart.js v2 options in a v4 project, Leaflet plugins for 0.7, three.js examples using Geometry (removed in r125). The fix is cheap if you recognise it: the error says "undefined", meaning the namespace exists but not that member.

Trap · the package that isn't

Check that the package exists, and is the one you think

  • Models sometimes invent plausible package names.
  • People register those names and publish malware into them (slopsquatting). Typos work too (typosquatting).
  • Before you add one: the npm page. A linked repository, weekly downloads, the last publish date, the maintainers.
two minutes

npmjs.com/package/name → repository → stars, issues, last commit. A package with 12 downloads and no repository is not your chart library.

~2:12. This matters more in projects with npm, where npm install runs install scripts on your machine. In a browser page the damage is limited to the page, which leads to the next slide.

Security

A library runs with all of your page's rights

It can read the DOM and localStorage, send fetch requests, log keystrokes. There's no sandbox between your code and theirs.

Subresource integrity: the browser refuses the file if a single byte changed.

~2:13. Libraries often publish the hash with their install snippet (Leaflet's download page does); or compute it: openssl dgst -sha384 -binary leaflet.js | openssl base64 -A. Works on <script> and <link rel="stylesheet">; import maps have an integrity section in newer browsers. Pin first: a hash for a moving version breaks on the next release. In 2024 the polyfill.io CDN was taken over and served malware to every site still loading it: the case for integrity, and for the next slide.

Vendor it: a copy in your repository

  https://esm.sh/d3@7.9.0/es2022/d3.bundle.mjs

# the import map points at it
"d3": "./vendor/d3-7.9.0.mjs"
  • Works offline, on any Wi-Fi, forever.
  • The version is frozen and visible in the repository.
  • Check it's one file: jsDelivr's d3@7.9.0/+esm is 1.5 kB that imports 30 more. esm.sh's d3.bundle.mjs has everything.
  • CSS, fonts, and data files too.

~2:14. Test it: DevTools → Network → Offline, reload. Anything that fails is still on a CDN. The same goes for API data: a cached JSON file in the repo beats a live API on a bad connection.

npm and a bundler

What npm and a bundler add

  • npm install d3: into node_modules, exact version in the lockfile. Commit the lockfile.
  • ^7.9.0: any 7.x from 7.9.0. ~7.9.0: only 7.9.x.
  • A build tool like Vite (bundling with Rollup and esbuild): dev server, bare names, TypeScript, minifying, dropping unused code.
  • The output is still static HTML, CSS and JS.
  • Next: your own code as packages, and frameworks built on all of this.

~2:16. One slide so the words are familiar. A page with an import map and no build step is a complete, deployable project; a bundler earns its place when there are many dependencies, TypeScript, or a lot of code to split and minify.
